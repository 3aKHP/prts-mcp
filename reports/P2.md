## 架构：config↔activation 循环的消解

TS 的 `config.ts ↔ activation.ts` 互引（loadConfig 每次调用做激活检测 + 快照钉住）在 Rust 里按 docs/02 的结构调整方案拆开：

- `RuntimeConfig`（`src/config.rs`）：启动一次解析的静态路径/开关（含 `PRTS_AUTO_SYNC_INTERVAL_SECONDS`、`GITHUB_MIRRORS`、`GITHUB_TOKEN` 不记录日志）。不 import app/domain/sync/storage。
- `DataState`/`DataView`（`src/app.rs`）：动态代际解析。每次工具调用取一次 `Arc<DataView>` 快照（TS `withActivationSnapshot` 的对应物），以指针文件 stat 签名（pair + 两个 extract_meta 的 ino/size/mtime/ctime，对应 TS `activationPathToken`）缓存；签名变化即重解析。同一快照整次查询有效（"list_stages 跨更新仍同代"），在途查询持有的旧代目录因 24h retention 仍可读。
- 同步完成后**无需显式失效**：激活重写指针文件 → 下一请求签名不同 → 新快照。进程级证据：`missing_data_background_sync_readable_without_restart`（同进程从缺数据提示变为与 TS golden 逐字节一致的输出，无重启）。

## 锁协议与层级

目录 owner 租约逐项移植（`src/sync/activation.rs`）：mkdir 抢占 → 写 `owner` 文件（32 hex）→ 心跳任务按 `heartbeat_ms` 在仍持有时 `utimes` owner → 陈旧（`stale_ms`）或无主超宽限（`owner_grace_ms`）时改名 `.stale-<uuid>` 隔离后删除 → 释放前重读 owner，仅仍属本方才删除（旧 owner 不能删接班者锁）。默认常量与 TS 一致：等待 120s / 陈旧 30min / 无主宽限 10s / 心跳 60s / 轮询 50ms / 代际保留 24h。symlink 锁拒绝。

调用层级（docs/05 顺序）：`.gamedata-pair.lock`（共同父目录）→ excel `.activation.lock` → excel `.release.lock` → 释放 → levels `.activation.lock` → levels `.release.lock`。Story 独立 `.release.lock`；`.images.lock` 原语已支持（P6 接入）。

跨进程证据（`cross_process_lock_contention`）：TS（真 dist `withArchiveActivationLock`）持锁 → Rust 争用超时且**不删除存活锁** → TS 释放后 Rust 获得锁；反向 Rust 持锁 → TS 争用超时 → 释放后 TS 获得。锁 owner 转换即此四步。

## 传输与调度

- 直连先试（经环境代理），网络/5xx 才镜像；direct 404 = typed absent（manifest 旧发布兼容分支**仅** non-datarev）；其他 direct 4xx 停止；每候选独立超时（10s 发现 / 120s 资产）。
- **流式下载**（docs/02 批准的技术债修复）：资产写 tmp 文件并增量 sha256（不二次读文件），ZIP 按条读取——见峰值测量。失败保留旧 zip。
- 调度（`scheduler.rs`）：启动周期各数据集 single-flight 并发执行；`offline_fallback/no_data` 才触发 30/120/600s 密集重试（**仅启动轮**，周期轮 forceCheck 不武装重试——与 TS 相同）；`PRTS_AUTO_SYNC_INTERVAL_SECONDS` 解析含 `+/-整数` 拼写、0=仅启动、越界回退 3600s 并告警；周期在本轮结束后排下一轮不重叠；custom GAMEDATA_PATH / 非空 STORYJSON_PATH 分别关闭对应同步（空字符串仍启动 story 同步——JS falsy 语义）。重试/定时器全部为 spawned task：`stdio_exit_with_pending_retries` 证明 30s 重试已武装时 stdio EOF 仍 <10s 内退 0。
- gamedata pair 重试规则保留：仅 offline/no_data 密集重试，commitSha 不匹配不触发（#102）。

## 同步峰值测量（artifacts/p2-bench.json）

固定输入：pin 的真实发布 `datarev-26-10-08-04-51-28-56071834-r2`（excel 10.5MB + levels 14.2MB + story 35.9MB ≈ 60.6MB），本地 ghproxy 式镜像（直连经死代理强制级联），3 轮（docs/06 重型同步至少 3 轮），release 构建。

| 场景 | wall (median) | VmHWM 峰值 RSS (median) |
|---|---|---|
| Rust 冷同步（三数据集全量） | 1006 ms | **23.1 MB** |
| Rust 无变化周期（fresh 跳过） | 454 ms | 20.7 MB |
| TS 冷同步（同代码 dist，node 运行） | 3805 ms | 320.9 MB |

结论按实测量写：Rust 峰值 ~23MB 显著低于 60.6MB 包体——流式下载 + 按条 ZIP 读取使峰值不随包体线性增长，满足"不能保持整包多份缓冲而声称完成内存优化"。TS 腿为对比参照：其 `arrayBuffer` 整包缓冲 + AdmZip 解析路径峰值 ~321MB。诚实披露：TS 腿在 node 下运行（Bun 忽略代理环境变量，无法确定性指向本地镜像；dist 代码同一，transport 的 undici 代理分支本就为 node 编写）；node 基线运行时占数十 MB，比较应看相对包体的增量而非绝对差。全部样本、min/median/max 与方法学记录在 artifact。
