## 目标与范围

用已经公开的 Rust 候选在真实 MCP 客户端中完成一次用户使用、数据同步、图片展示和旧版升级/回滚流程，修复实际发现的迁移阻断问题，并形成维护者能够判断是否进入 M5 的报告。优先在现有 WSL 主机执行；Windows 侧可补充真实客户端或原生运行证据。只认领实际执行的平台，Linux ARM64/macOS 的既有平台证据引用 M2/M3，不重新跑五平台真机矩阵。

维护者已要求减少发布阻力：不新增独立验证门禁、发布权限探针、定时验收或常规额外矩阵；只有真实事故才讨论新增机制。M4 是已约定的一次迁移验收，不变成每次发布的全量前置流程。修复后只复验受影响环节；已有正确证据直接复用。

本轮先做 M4。完成后交接独立文档专场，再进入 M5；不夹带 CLI、功能新增、AKDP 改造、crates.io 发布或稳定渠道切换。data/ 方案已经冻结，本轮补齐其运行证据，不重新设计数据分发。

## 流量原则：大包复用，小流量实测

本机网络事实（维护者于 2026-10-14 明确）：Windows Clash 对 WSL 全部出站流量做规则代理，任何实际访问 github.com 的流量都会计费。取消 HTTP_PROXY/HTTPS_PROXY、设置 NO_PROXY、使用 curl --noproxy 或从 WSL“直连”GitHub 都不能绕过这项计费。计划不提供本机免费直连 GitHub 的方案；GitHub API、资产重定向/CDN、GHCR 等相关外部路线也不能未经确认就认作免费，Windows 侧运行或换下载工具不改变这个默认判断。

同日已只读核对正在运行的 verge-mihomo 的 -f 所指运行配置，而非仅查看订阅模板：mode=rule，TUN enable/auto-route 为 true、stack=gvisor，DNS 为 fake-ip（198.18.0.1/16），mixed-port=7897。DOMAIN-KEYWORD,github 指向代理策略，覆盖 github.com、api.github.com 及常见 githubusercontent.com 资产域名；最终 MATCH 也指向代理策略。127.0.0.0/8 有 DIRECT 规则。本次未发起外部探测，配置只证明规则意图，不提供收费计数。配置另有部分 Windows 下载器的进程 DIRECT 例外，本轮 WSL Rust/npm 流程不据此认领免费路线，也不擅自换工具下载大包。未修改配置，订阅、节点地址/凭据和完整规则不写入仓库。

默认方案是不新增经计费代理下载的整套美术资产。公网只做真实使用所需的少量 Wiki/单张图片调用，以及必要的上游元数据观察；禁止全干员图片抓取、强制全量刷新、重复冷启动下载、无界自动重试。发现下载路线不明或缓存不足时，先完成不依赖下载的任务，把待下载对象、压缩字节数、路线与必要性合并成一次维护者选择，不自行启动 GB 级传输。

日常回放不访问真实 GitHub/API/资产 CDN：候选的真实源尝试通过子进程失败代理在 WSL 本地立即失败，再进入只读本地镜像；localhost 请求路径中包含 https://github.com/... 只是镜像的资源键，不产生 GitHub 网络访问。复用本地 Release 清单与 M3 回执，不为核对版本再打开 GitHub Release、调用 gh release download 或重新拉取候选镜像。若确有必要新增外部获取，按潜在计费请求记录，不能记作“直连免费”。

“本地有 3.1 GB”描述的是两个解压后的立绘卷合计占用，既不是本轮需要下载的量，也不是原始包下载大小。磁盘复制、localhost 镜像传输与公网代理流量分别记录。若执行 Agent 在另一台机器上，优先让它远程操作现有 WSL；其次通过确认不计费的局域网/本地介质搬运一次。把缓存经同一计费代理传到新机器并不省流量。

## 步骤 2：准备一次本地数据源并限制外部下载

复用 tools/images-mirror.mjs 的镜像协议：在任务目录下准备 releases.json 和 assets.txt，后者每行为“完整上游 URL + 空格 + 本地相对文件路径”。复制或链接只读原始游戏 ZIP/manifest，使用固定 datarev tag，releases.json 包含对应 asset 的 browser_download_url。镜像不转发未知 URL 到公网，未命中直接返回失败。需要记录请求与字节时，在任务脚本中补简单日志即可，不增加产品配置或监控系统。

现有镜像在启动时一次读入 releases.json/asset 映射，改文件不会改变正在运行的响应。分阶段更新采用一个保持地址不变、按请求读取阶段文件的薄任务脚本，或明确重启镜像并更新读取它的测试进程配置；同进程缓存失效案例使用前者。这个辅助脚本只服务本地回放，不能进入生产发行物，也不扩展成独立验证框架。

注意两个现有行为：GITHUB_MIRRORS 是“先尝试真实 GitHub，失败后尝试镜像”，不是强制改写源；PRTS_AUTO_SYNC_INTERVAL_SECONDS=0 只关闭周期检查，启动同步和启动失败重试仍然存在。因此，设置本地镜像之后直接启动仍可能消耗公网大包流量。所有同步回放子进程必须同时使用仅对子进程生效的本地失败代理，NO_PROXY 仅放行镜像地址，不能包含 github.com/API/CDN、通配符或全域名绕过；先确认所选失败代理端口没有服务。当前 Rust transport 的 reqwest 客户端读取这些代理变量，真实源的 TCP 连接目标会是本地失败代理，不是外部 GitHub；错误后才尝试镜像。这个措施用于阻止外部请求，不是通过 Clash 免费直连。不要改全局代理、TUN、DNS 或系统环境。

下面是 WSL HTTP 回放的启动模板，变量须先按任务目录及镜像打印的端口填写；M4_BLOCK_PROXY 指向已确认无监听的 localhost 端口，示例为 http://127.0.0.1:9。

```bash
# M4_BIN：已解压公开候选 bin/prts-mcp 的绝对路径。
# M4_ROOT：唯一测试目录；M4_MIRROR：http://127.0.0.1:<实际镜像端口>。
# M4_BLOCK_PROXY：http://127.0.0.1:9，执行前确认该端口无服务。
env -u GAMEDATA_PATH -u STORYJSON_PATH -u PRTS_TRANSPORT -u PRTS_MCP_ROOT \
  XDG_DATA_HOME="$M4_ROOT/user-data" \
  GITHUB_MIRRORS="$M4_MIRROR" \
  HTTP_PROXY="$M4_BLOCK_PROXY" HTTPS_PROXY="$M4_BLOCK_PROXY" \
  ALL_PROXY="$M4_BLOCK_PROXY" http_proxy="$M4_BLOCK_PROXY" \
  https_proxy="$M4_BLOCK_PROXY" all_proxy="$M4_BLOCK_PROXY" \
  NO_PROXY="127.0.0.1,localhost,::1" no_proxy="127.0.0.1,localhost,::1" \
  IMAGES_ENABLED=true LOCAL_IMAGE=true ORIGINAL_IMAGE=false \
  PRTS_AUTO_SYNC_INTERVAL_SECONDS=0 HOST=127.0.0.1 PORT=39173 \
  "$M4_BIN"
```

镜像及图片回放包必须先就绪；最初只做游戏同步时将 LOCAL_IMAGE=false，并让外部请求仍走失败代理，图片工具的在线读取留待步骤 6。39173 只是示例，检查端口空闲后选择。主命令不显式指定传输，以验证默认 HTTP；stdio profile 则显式设 PRTS_TRANSPORT=stdio。真实客户端连接 http://127.0.0.1:39173/mcp；日志保存 stderr，避免把启动日志混入 stdio 的 MCP stdout。

自然同步时必须不设置 GAMEDATA_PATH 和 STORYJSON_PATH；设置 GAMEDATA_PATH 即使为空也会关闭 GameData 自动同步。WSL 用 XDG_DATA_HOME 隔离；Windows 原生用子进程/客户端 profile 的 LOCALAPPDATA 隔离，不能只设置 XDG_DATA_HOME。Docker 写 /data，不使用 XDG_DATA_HOME 隔离，必须挂载任务专用卷；受控同步使用没有公网出口的 internal network 及网络内镜像。容器内 localhost 不是宿主镜像地址，NO_PROXY 应包含实际镜像主机名/IP。

仅清空代理变量或 curl --noproxy 不能证明流量不计费，本机的 Windows Clash 规则代理已经明确存在。实时小流量步骤按现有路线执行并记录为实际外部访问；本机不尝试大包直连。若候选包装器、旧版进程或容器没有继承/遵循回放隔离配置，停止该进程的同步，继续用已有数据做不依赖同步的案例，不通过恢复 GitHub 连接来补救。Docker daemon 的 pull 不受容器内代理变量控制，继续使用已缓存镜像与 --pull=never；不为本轮改变 Windows Clash 规则或增加系统网络隔离设施。

## 步骤 3：一次准备真实立绘回放包

优先查找是否另有完整、可追溯的原始 baseline/delta ZIP；若没有，按下面的本地重建方案执行。缓存根不是活动图片文件所在目录，先读取 ts-volume/.images_meta.json 的 generation_root，再读取该代际 index.json。保留旧 TS 原卷只读，以其中 PNG 为来源，按 index 的 file、bytes、sha256 字段验证重建输入；原图缺失不补下载。先准备回放包，实际同步与步骤 4/5 共用一个主测试 profile：先做无网络备用查询，再做游戏同步，最后在同一测试卷做图片 baseline/delta，避免另开多套全量同步。

1. 在任务目录生成 chararts-large、chararts-preview、skinpack-large、skinpack-preview 四份 baseline ZIP，只收录 sinceVersion 不晚于 baselineVersion 的对应真实 PNG；将其余真实 PNG 收入一份当前版本的合并 delta ZIP。ZIP 内路径使用 index 的相对 file，不包含活动卷前缀、绝对路径或上层目录。流式生成或 ZIP_STORED 即可，不将所有图片读进内存，也不重压缩多轮。
2. 生成镜像 asset 映射、对应 releases.json 和 index。保留真实完整 current index；如果需要分阶段增量，另生成明确标为“本地重建”的 baseline 阶段 index：currentVersion 为 baselineVersion，artworks 只含 baseline 集合。baseline 的发现记录使用 images-<baselineVersion>，另保留 images-baseline-<baselineVersion> 的 ZIP 地址；后续阶段再暴露 images-<currentVersion> 及合并 delta。created_at 按阶段递增，tag 与对应 index.currentVersion 一致。
3. 最初镜像只暴露 baseline 阶段，候选从空图片目录自然同步四个 shard，客户端读取一幅真实图并形成缓存；随后暴露完整 current index/delta，通过已文档化的同步触发方式更新，验证新代际、新 artwork 和缓存失效。如果用重启触发，要另用同进程小回放或既有生命周期检查补充缓存失效，不能把进程重启本身当成缓存失效证明。
4. 镜像记录确认增量阶段只取 index/待应用 delta、不再次下载四个 baseline；再启动相同版本确认 up-to-date。失败案例在独立小回放副本中暴露一个明确标为测试数据的下一版本，使 delta 下载或哈希失败，确认旧代际仍可读；恢复本地镜像后只重试受影响阶段。不在已经 up-to-date 的版本上期待发生下载，也不为故障测试重跑全部大包。
5. 汇总来源 index、PNG 校验、重建包大小/哈希和请求记录，标明“真实 PNG、本地重建历史”，不得标为原始 AKDP baseline/历次 delta。已存在图片被历史修改前的字节、原始多次 delta 排列及公网 ZIP 获取没有因此得到验证。

GameData 与图片可以共用一个镜像，但 releases.json 要同时包含需要的固定 datarev、images 阶段及 baseline 记录。将回放列表控制在少于 100 条，并包含链起点；现有镜像对所有 API 页返回同一列表，不可直接塞入完整上游百条列表造成重复分页。所有流量仍在本地，禁止镜像 miss 转发公网。

可以参考 tools/prepare-ts-images-volume.mjs 的 ZIP/index/asset 格式，但它默认生成小型合成 fixture；tools/verify-p8-lifecycle.mjs 默认调用源码构建的 prts-mcp-rust；二者均不能原样跑完后声称候选真机 E2E 完成。禁止运行 tools/bench-p6-images.mjs 来“补验收”：它会重新走公网并分别准备 TS/Rust 的大图卷。既有五图 fixture 只用于失败/边界案例，包含的伪 PNG 不能作为客户端真实图片展示证据。

## 步骤 4：发行入口与 data/ 运行证据

先完成原生包的空用户目录、外部网络不可用启动：备用数据能查询阿米娅、一个实际关卡及故事；安装目录不被写入。再启用本地游戏镜像，不设自定义数据路径，让生产候选自然同步原始 excel/levels/StoryJson ZIP，确认目录、pair pointer、版本元数据和查询均正确。镜像断开后在同卷重启，确认数据仍可读，未损坏已激活代际。

用户数据优先必须有可区分的结果；候选备用包与固定同步 ZIP 原本同版，单看版本一致不能证明优先级。在独立测试副本里给一项已选数据做可识别且结构有效的测试标记，用查询确认实际读取用户副本，并记录人为标记来源；不改候选安装目录或真实数据来源。缓存/锁/失败案例也用测试副本，禁止在用户原卷上制造损坏。

| 入口 | 本轮检查方式与复用范围 |
| --- | --- |
| 原生 prts-mcp | 主路径：默认 HTTP、完整游戏/图片同步和真实客户端调用。显式 stdio 补连接、代表查询和退出。 |
| npm prts-mcp | 复用已安装公开候选；默认 HTTP 与显式 stdio，空用户目录备用查询，以及已同步用户卷优先读取。 |
| npm 旧三个命令 | prts-mcp-ts、prts-mcp-ts-bun 为 HTTP，prts-mcp-ts-stdio 为 stdio；选代表工具、中文输出和关停，无需再次全量同步大图。 |
| GHCR 候选 | 使用已拉的本机实际候选镜像，docker run --pull=never；默认 stdio、显式 HTTP、备用读取和持久化卷重建。整卷与旧四子卷均用任务副本，不重跑整套 Docker 平台 probe。 |

需要独立 npm 测试安装目录时，先使用既有 cache 做 npm install --offline --ignore-scripts，固定两个入口的精确版本；缓存不足立即记录，不自动改为联网重试。已有安装目录可直接用于运行证据；不要修改该目录的 package/数据。无 Node/Bun/编译器依赖的原生与容器证据继承 M2/M3，本轮若无真实回归不再重验整套哈希、许可证或发行认证。

共享已经同步的数据副本给其余入口，避免“两个入口 × 两种传输 × 容器 × 新旧版本”重复全量下载/解压。完整 24 工具只在选定主 profile 做一轮；不同入口补其配置、运行时与生命周期区别。实际旧 TS/npm 回滚与旧 GHCR/Python 容器回滚分别记录；只执行前者时不可宣称后者也已通过。

## 步骤 5：真实客户端、工具与协议

用主 HTTP profile 连接真实客户端，开启 IMAGES_ENABLED=true，tools/list 应为 24。由实际 list/search 输出选择 ID，再执行相应 get/read；不要猜造干员、敌人、关卡或故事 ID。参数以候选 tools/list 返回的 schema 为准。可以使用客户端提供的手动工具调用能力，避免让 LLM 反复复述大段输出，但要保留一次真实用户交互和可见图片显示的记录。

| 工具组 | 本轮调用 |
| --- | --- |
| Wiki | search_prts、prts_page；在线步骤统一放到步骤 6。 |
| 干员 | get_operator_basic_info（basic/skills/stats 分支）、get_operator_archives、get_operator_voicelines、get_operator_memoirs。 |
| 物品/敌人/关卡 | list_items、get_item_info、list_enemies、get_enemy_info、list_stages、get_stage_info、get_stage_enemies、get_enemy_appearances。 |
| 故事 | list_story_events、list_stories、get_story_summary、read_story、read_activity、search_stories、find_character_appearances、find_speakers_in。 |
| 综合搜索 | search；用中文及既有正则契约的代表案例。 |
| 立绘 | operator_artwork：先 list 获得 opaque artwork ID，再 get large/preview，实际解码并在客户端显示真实图片。original 无缓存时只验证可理解的未可用行为。 |

对缺数据、非法输入和网络失败各选代表场景，确认提示可理解且服务继续工作；不把每个工具机械排列全部异常组合。关闭图片后确认 23 工具可继承/补一例，不再做第二轮全工具测试。

现代与 legacy 协议用真实客户端能覆盖的版本加现有轻量 harness 补齐；记录哪部分由客户端、哪部分由 harness 完成。检查 HTTP 会话初始化/续用、非法会话或鉴权拒绝、会话结束；stdio 的 stdout 仅有 MCP、stderr 记日志、EOF 正常退出；Unix 信号及 docker stop 实测进程/退出状态，Windows 只认领实际执行方式，不把 OS 终止写成 graceful shutdown。鉴权涉及的临时令牌只在任务环境使用，报告中不保留值。

## 步骤 6：集中完成少量实时上游调用

完成本地同步后，为真实 Wiki 路径启动独立读取 profile：LOCAL_IMAGE=false、IMAGES_ENABLED=true；明确 GAMEDATA_PATH 与 STORYJSON_PATH 指向已准备的完整测试数据，关闭这一读取 profile 的无关游戏自动同步。这里只是读取案例，不算自然同步。恢复该子进程原有可用网络路线，仍保持周期同步为 0，整个步骤结束就停止进程。

真实客户端做一次 search_prts、一次 prts_page 和一个干员的 operator_artwork list/get；选 preview 或已确认大小的单张图片，再取同一图片观察缓存。必要时增加一次失败恢复，不抓取所有条目。记录上游地址、请求次数、响应/下载字节以及实际路线；避免在报告或聊天中重复输出完整 base64。图片证据保留本地文件、SHA256、尺寸及客户端显示截图/短说明即可。

GitHub/AKDP 的实时元数据调用默认省略，优先使用本地固定快照。只有需要确认真实上游变化或排查实际失败时，才单独读取一次必要的 Release 元数据/index，并作为可能计费的小流量记录；先看 asset.size，绝不直接启动带 LOCAL_IMAGE=true 的公网首次同步。这里得到的是“实时元数据可访问”，不是“原始大包已下载”。同一响应缓存下来供分析，不轮询新 release 或自动追最新数据。

已有代理统计可用于记录前后差值；共享主机后台流量可能影响差值，需要如实标注。没用现有可归属的计数器时，只报告可观察的请求/响应字节与路线，不编造精确收费值；不为本次验收搭建新的计量系统。

## 步骤 7：真实旧发行物升级与回滚

先用固定实际 2.8.1 发行物在专用测试环境读取旧 TS 卷副本，记录一个干员、关卡、故事和真实 large/preview 图片的基线结果；旧 TS 可使用原先所需 Node/Bun，但与 Rust 候选运行环境分开。不要仅调用冻结 oracle 后宣称“用户旧发行物可回滚”。

将旧测试卷另复制为升级工作卷，切换到公开 Rust 候选，确认原数据直接可用，再通过本地镜像完成一次游戏/图片更新与代际激活。验证共享锁不造成并发写坏、失败不激活半成品、更新后的查询/图片不受旧缓存影响。这些案例复用前面已准备的包，不能为旧版和 Rust 各重新下载。

停止 Rust，用固定实际旧发行物直接回读这份“被 Rust 使用和更新后的工作卷”；保留其 pair pointer、图片 generation_root 和元数据，不先删除 Rust 状态或还原旧备份。再次完成前述代表查询及图片读取，记录用户需要的启动/配置切换动作。恢复备份只能证明备份恢复，不能冒充兼容回滚。

容器整卷、四子卷的重建与回读复用旧部署布局，实际旧 GHCR 缓存可用时补充固定旧镜像回读；如缺旧镜像，给出下载尺寸/成本和未执行范围，其他项目继续。Windows 额外执行时从本地复制必要候选/测试数据，使用 Windows 自身路径隔离，不再次从公网拉全部资源。

## 步骤 8：修复、报告与交接

发现真实阻断时，先保留最小复现、涉及候选/数据版本及用户可见影响，再从 develop 短分支修复；不顺便重构无关代码。按既有 WORKFLOW 运行对应验证，触及 runtime/sync/协议等高风险域执行既有 check-runtime --full 与独立只读 CR。源码修复的本地复验记录为构建品结果；若公开 alpha.3 仍有阻断，不能把源码结果改写为 alpha.3 已通过，需要按现有候选发行流程处理一次确实必要的新候选。

提交、推送、开 PR、合并及新候选发布依执行会话的明确授权和现有仓库规则；本计划不是稳定发布或 npm 账号操作授权。维护者已明确 Bot 故障无需等待，该豁免不算 Bot 通过；需要独立 CR 的变更仍执行。短分支 push 不触发完整矩阵，PR 复用现有 CI；不另建 M4 workflow，不为了报告而手动重跑全平台或发行 run。

交付 docs/dev/reports/3.0-m4-e2e.md，内容包括下面五项；详细日志、截图与数据放在忽略的任务目录，报告只保留可审查的摘要和来源。

1. 环境、真实客户端、精确候选/旧版版本及来源，实际运行的平台/入口，命令与脱敏配置；附现有 M2/M3 证据链接，不再粘贴全套结果。
2. 按“工具/协议、备用与用户数据、自然同步、两条图片路径、增量/离线/关停、升级/回滚”列通过、失败、未执行，以及客户端/harness、原始 ZIP/重建包/合成 fixture 的来源区别。
3. 流量摘要：已复用的大包、局域网/本地传输量、实际新增公网请求及可观察字节，原图/原始历史未下载范围；不要用解压后 3.1 GB 充当代理用量。
4. 真实问题、修复/PR 与仅针对受影响部分的复验。无法访问客户端、原始美术历史或某平台时明确披露；只有既有范围已解决或维护者接受其取舍后，才把 M4 标为完成。
5. 给维护者的一个集中待办列表：确实需要手动客户端操作的项目、确实不可替代的新增下载及成本选择，以及是否可进入文档专场/M5；不得产生新的例行审批或验证门禁。

停止本轮启动的服务器、mirror 与容器，恢复临时客户端 profile；只清理明确属于任务的进程/网络。保留可复用的镜像、包、测试基线和原始缓存，禁止 docker system prune 或整目录清空。按真实结果更新 STATUS.md 和迁移总计划；data/ 运行项满足既定要求时可关闭其对应部分，独立文档工作未做则保持开放，不能因 M4 报告存在就认领文档专场完成。
