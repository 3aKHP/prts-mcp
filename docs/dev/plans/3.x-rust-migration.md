## 冻结决策

| 事项 | 维护者决定 |
| --- | --- |
| 技术栈 | Rust 是 3.x 唯一业务实现；不回退 Python、JS 或 TS 业务。原生 C 组件可以随发行物提供，用户无需配置编译器或原生库。 |
| 首发范围 | 仅完成迁移；不实现管理 CLI、配置文件体系、新工具、新数据域或 AKDP 专项。 |
| 源码布局 | 根目录原生 Cargo 工程。3.x 的 main/develop 不持有 python/、ts/ 目录；这两套实现留在 LTS 分支和历史版本中。 |
| npm | 新主包 prts-mcp；旧包 prts-mcp-ts 保留为兼容入口，共用同一版本的 Rust 核心和平台产物。新名称以注册成功为前提。 |
| 默认传输 | 新原生 prts-mcp 和 npm 主入口默认 Streamable HTTP，对齐 TS；stdio 继续支持。旧命令保留各自的默认行为。 |
| 首发平台 | Linux x64 glibc、Linux arm64 glibc、Windows x64、macOS arm64、macOS x64；Docker 同时覆盖 Linux x64/arm64。 |
| PyPI | 3.x 首发不新增 PyPI 包装；旧 Python 包在 2.x LTS 内继续维护，提供更换安装渠道的迁移说明。 |
| crates.io | 3.0 迁移期间准备独立源码打包；实际上架在 M5 完成后作为独立渠道任务，不阻塞 3.0 首发，也不必等待 3.1。 |
| 旧版维护 | 2.8.x 采用与 1.7 相同类别的 LTS 机制，EOL 同为 2027-07-02；暂不拆仓，明确分为 lts/2.8 与 lts/1.7。 |
| Docker | 保留 ghcr.io/3akhp/prts-mcp；3.0 正式发布时 latest 切到 Rust，旧版与预发布渠道隔离。 |
| 真机验收 | M4 执行一次完整真机 E2E，可在本机 Windows 侧和/或 WSL 完成；使用实际候选发行物和真实 MCP 客户端，并验证升级及回滚。 |

已批准的 Rust 行为差异继续按原账本披露和验证，不在迁移中重新否定或静默扩大。TS/v2.8.1 是业务比较基线；Python/GHCR 只提供旧容器入口、卷、权限和回滚参照。

## 主仓布局

目标布局为根目录原生 Rust 项目，目录细分遵循已有模块边界：

```text
PRTS-MCP/
├── Cargo.toml
├── Cargo.lock
├── rust-toolchain.toml
├── build.rs
├── src/
├── tests/
├── vendor/
├── contracts/
├── packaging/             # npm 启动包装及平台包模板
├── tools/                 # 验收与打包工具，按需要导入
├── scripts/               # 支持的开发与发布入口
├── Dockerfile
├── CHANGELOG.md
├── docs/
└── .github/workflows/
```

共享 fixture、许可证、NOTICE、数据声明和重建验证所需的契约快照一并盘点，不能只搬 src/。完整下载数据、编译缓存、node_modules、凭据和原始大体积日志不进入 Git。根目录不要求存在 Node package.json；npm 的元数据放在 packaging/。

导入保留 Rust 提交历史。实施采用不 squash 的 subtree 暂存导入，再重定位到根目录；在隔离 feature 分支验证冲突和路径处理，不复制嵌套 .git，也不以嵌套 AGENTS.md 覆盖主仓规则。原本地仓库和 bundle 保留为核对来源。

JS 可以用于开发验收及 npm 薄启动器，负责定位二进制、转发参数、标准流、信号和退出码；不保留 JS/TS 业务实现。历史 TS oracle 从固定 tag 在忽略目录或独立 worktree 中重建，不要求 3.x 主树继续存在 ts/。

## 分支与 LTS

| 分支 | 代码归属 | 发布与维护 |
| --- | --- | --- |
| main | M5 前仍为 2.8.1；3.0 发布合入后为根目录 Rust 工程 | 最新稳定线。 |
| develop | M1 迁移合入后为根目录 Rust 工程，目标 3.0.0-dev.0 | Rust 开发集成线。 |
| lts/2.8 | Python 和 TS 两套 2.8.x 实现及其完整构建资源 | 双实现 LTS，EOL 2027-07-02。 |
| lts/1.7 | 既有 1.7.x 双实现 | 既有承诺及 EOL 2027-07-02 保持。 |

先从稳定 2.8.1 提交保留 lts/2.8，再使 develop 转为 Rust。M1 不提前改变 main 的稳定实现。若启动时已有新的 2.8.x 稳定补丁，重新固定该稳定提交与修复移植清单。

2.8 LTS 接受兼容性、安全性、数据同步、关键缺陷及对应文档修复，不接受新能力。修复从 lts/2.8 拉短分支、PR 回 lts/2.8，Python/TS 继续保持契约与版本锁步。适用于 3.x 的修复另开 Rust PR；禁止把旧分支整体合并到 Rust develop。

在 main 尚为 2.x、develop 已为 Rust 的过渡期，main 上的 2.x hotfix 应同步至 lts/2.8，并在 Rust 中按适用性重做；不能沿用会将 python/、ts/ 带回 develop 的整体 forward merge。

LTS 不更新 npm latest、Docker latest 或 GitHub Latest。EOL 后停止两条 LTS 的新发布并保留历史代码和发行物；1.7 数据投影依现有政策处理，AKDP 为 3.x 提供数据的工厂不因旧版 EOL 停止。

## 入口与发行渠道

| 入口 | 默认传输与兼容约束 |
| --- | --- |
| 原生 prts-mcp | Streamable HTTP；通过 PRTS_TRANSPORT=stdio 显式选择 stdio。未设值使用 HTTP。新入口的非法值回退等细节在 M1 固定并测试。 |
| npm prts-mcp 的主命令 | prts-mcp，采用新原生入口。 |
| prts-mcp-ts、prts-mcp-ts-bun | 保留旧 TS HTTP profile；旧 bin 名不意味着运行 TS/Bun 业务。 |
| prts-mcp-ts-stdio | 保留旧 stdio profile，不启动 HTTP listener。 |
| 既有 GHCR 兼容入口 | 保留原镜像的默认 stdio、PRTS_TRANSPORT=http 选择规则、环境变量、卷和权限契约。 |

主命令默认 HTTP 与 GHCR 兼容入口默认 stdio 分别持有 profile。迁移当前本地名为 prts-mcp 的 GHCR 入口时，必须把它改为显式的容器兼容 profile，不能让文件名与新主命令的默认值冲突。仅切换默认值不等于重写 MCP 协议。

两个 npm 入口包使用同一套按平台分发的 Rust 二进制，版本精确对应。新包提供新主命令，旧包提供三个旧命令，避免同时安装时争抢同名 bin。必要的共享启动器可以复用，不复制两套业务或二进制构建流程。

| 渠道 | 3.x 策略 | 旧版隔离 |
| --- | --- | --- |
| npm | 预发布使用 next；3.0 正式发布后新主包及旧兼容包 latest 指向对应 Rust 发行版。 | prts-mcp-ts 的 lts-2.8 跟随 2.8.x；lts-1.7 保持。历史版本不重写。 |
| 原生程序 | GitHub Release 提供五种目标平台的可执行产物、许可证和校验清单。 | 历史发行物保留。 |
| GHCR | 预发布仅推进候选标签；正式版提供精确版本、3、latest。 | 2 跟随 2.8 LTS；1.7 维护标签遵循既有隔离规则。 |
| PyPI | 不发布 3.x 包装。 | Python 2.8 LTS 和 1.7 LTS 保持各自维护与发行规则。 |
| crates.io | M5 完成后发布当时已验收的稳定版本；迁移期间只准备元数据与独立源码包。 | 不替代 npm、原生程序或 Docker 的预编译安装路径。 |

3.x 采用单一产品版本和 v3.x.y tag；预发布形式为 v3.0.0-alpha.N/beta.N/rc.N。Cargo、npm 入口/平台包、容器及协议中的产品版本必须一致。旧分支继续 python/v2.8.x + ts/v2.8.x 以及 1.7 的成对 tag。现行裸 tag 禁止与双实现锁步规则仅在相应 PR 修订并合入后对 3.x 改变。

固定版本或固定 major 的用户不会被 dist-tag 自动迁移。迁移文档区分裸安装、@2、@lts-2.8、精确版本及 Docker latest/固定版本；不承诺所有用户自动升级。

## 平台与分发验证

| 平台 | 构建目标 | 必需证据 |
| --- | --- | --- |
| Linux x64 glibc | x86_64-unknown-linux-gnu | 原生安装、npm 安装、真实运行及容器验证。 |
| Linux arm64 glibc | aarch64-unknown-linux-gnu | 原生安装、npm 安装、真实运行及 arm64 容器验证。 |
| Windows x64 | x86_64-pc-windows-msvc | 原生与 npm 安装运行、标准流和退出行为。 |
| macOS arm64 | aarch64-apple-darwin | 原生与 npm 安装运行、权限、标准流和退出行为。 |
| macOS x64 | x86_64-apple-darwin | 原生与 npm 安装运行、权限、标准流和退出行为。 |

Linux 的最低 glibc、其他系统最低版本及 CPU 基线在 M2 按实际部署与构建证据确定。发行物携带需要的原生组件，不能要求终端用户现场编译或安装开发库。仅交叉编译成功不足以声称运行支持；模拟环境与原生环境分别标明。

Windows CRT 及其他额外运行库应静态链接或随包提供，并在没有开发工具链的环境验证；不能把用户另装运行库作为正常安装步骤。Linux 验证实际 ELF 依赖及最低符号版本，避免只在构建机能运行。

完整 E2E 在本机 Windows 和/或 WSL 执行。macOS 及 Linux arm64 的平台安装/运行验证由对应 CI runner 或其他可用环境完成，不能以本机 E2E 代替。Windows arm64、musl/Alpine 和其他平台不列入首发支持。

npm 的平台选择、全局安装、npx、干净缓存、锁文件安装、缺少平台依赖的诊断、信号与退出码均需验证。二进制通过 npm 平台包分发，避免另造依赖 GitHub 下载及本机编译的正常安装路径。现有 Node/npm 是 npm 启动路径所需环境；直接原生程序和 Docker 不依赖它们。

crates.io 面向已有开发环境的源码安装用户；cargo install 会本机编译，本项目因此需要 Rust 与 C 工具链。M1–M2 整理独立源码包的文件清单、许可证、原生源码、契约文件和最低 Rust 版本，并验证打包后能独立构建。M5 后另行完成渠道权限、源码安装、首次数据同步及发布自动化验收；推荐安装命令采用 --locked 复用随包锁文件。定位为服务应用的源码分发，不扩展为新的 SDK 项目。

M0 的 cargo package --list 检查发现本地 Rust 仓库有一个被 Git 跟踪、文件名含特殊字符的遗留文件，导致源码打包失败；M1 导入盘点时处理，不将它搬入正式主树。独立源码包检查见 [Cargo 打包说明](https://doc.rust-lang.org/cargo/commands/cargo-package.html)，源码安装与锁文件行为见 [Cargo 安装说明](https://doc.rust-lang.org/cargo/commands/cargo-install.html)。

## 验收与回滚

2026-10-13 维护者追加两个正式发布门禁：① 单独开展文档工作，对照 2.x 仍适用的用户/开发文档，恢复内容覆盖并更新为真实 Rust 安装、使用、维护和迁移说明，不能只保留简短入口或把历史归档当作当前说明；② 重新确定根 data/ 的源码管理、发行物携带、首次同步、运行时可写路径与旧数据兼容方案，并按最终方案验证。两项不阻断或打断 M2A，在 M2A 之后作为独立事项推进；若 data/ 决策影响 npm/Docker 包装或候选产物，须在相应产物验收前落实。M5 正式发布之前必须均有明确方案、实施结果和验证证据，不将其延期至 3.0 之后，也不把 M2A 的临时 fixture/打包方式视为最终 data/ 决策。
