# ADR-0001：3.1 引入实验性 SQLite 数据后端

- 状态：Accepted（3.2 阶段的落地语义见 [ADR-0018](ADR-0018-sqlite-default-with-json-fallback.md)）
- 决策日期：2026-10-18
- 关联：[Issue #263](https://github.com/3aKHP/prts-mcp/issues/263)、[CHANGELOG 3.1.0](../../../CHANGELOG.zh-CN.md)、[contracts/sqlite-schema-v1.sql](../../../contracts/sqlite-schema-v1.sql)

> 本文整理自决策期间（2026-10-17 至 2026-10-18）的内部工作记录（PoC 报告、迁移计划与验收回执）。文中测量数字为决策时在 Linux x64 开发机上以进程 RSS 与毫秒延迟口径取得的快照，仅作决策依据存档，不构成跨平台性能承诺。

## 背景与问题

3.0 起服务端的数据层以 JSON/ZIP 文件为唯一存储形态，按代际持有整表内存缓存。三个记录在案的因素共同促成了对存储后端的重新评估：

- **运行时内存**：JSON 路径的常驻内存随游戏数据量增长，预研立项时即将降低运行时内存列为首要目标，磁盘占用允许适度增加。
- **冷查询路径**：2026-10-15 的内部记录显示，当时候选版（3.0.0-rc.2）在生产环境的首次敌人出场查询服务端耗时 34.25 秒并导致客户端超时，受控重启后首次查询仍约 5.1 秒；根因是该查询需要完整解析全部关卡 JSON 再建索引。3.0.0 正式版以字段投影等最小优化缓解但未消除根因，同类冷路径问题需要结构性手段。
- **剧情全文扫描的资源有界化**：长文本正则扫描在 JSON 路径上与普通查询共享内存与计算资源，需要可隔离的执行通道（[ROADMAP.zh-CN.md](../../../ROADMAP.zh-CN.md) 对此有公开表述）。

约束：冻结的工具契约、正则语义、剧情语料与排序结果不得改变——任何存储层改动都必须通过 384 项冻结差分验证。

## 备选方案

- **DB-only 切换（按 4.0 Major 组织）**：默认且唯一消费 SQLite，停止读取旧 JSON 卷与自定义 JSON 路径。该方案已完成完整本地实现，但在决策当日搁置：直接停读旧数据卷属于公开契约的重大变更，按 [VERSIONING.md](../VERSIONING.md) 应走 Major 版本而非塞入小版本；实现本身保留为历史证据。
- **逐行 SQL 全文扫描**：剧情逐行存储、逐行匹配，PoC 实测约慢 5 倍，弃用。
- **FTS5 trigram 全文索引**：不能覆盖现有正则语义与短中文查询，不作为首版方案。
- **单连接 SQLite**：并发实验显示 4 个长扫描会把普通查询拖慢约 8 秒，据此改为扫描与普通查询连接分离、异步排队。
- **仅 JSON + 局部优化**：无法达成内存数量级目标，未采纳。

## 决定

自 3.1 起引入与 JSON 并存的实验性 SQLite 数据后端，分阶段推进：**3.1 默认 JSON、显式启用 SQLite；3.2 在生产试运行后翻转普通默认值；3.x 持续支持 JSON。**

落地语义：

- `PRTS_DATA_BACKEND=json|sqlite` 在启动时固定，非法值拒绝启动；`PRTS_DATA_DB` 指向预编译离线 DB 时等同选择 SQLite；与显式 JSON 冲突时报错。
- 两个后端互斥：每个进程只读取、同步、缓存所选后端；SQLite 缺失时不静默回落 JSON，JSON 模式不打开 DB。
- 发行包内置备用数据保持 JSON；离线使用 SQLite 需管理员预置 DB，在线模式仅下载 DB 的 gzip 制品。
- 不自动转换旧数据卷，不删除另一后端的数据。
- 上游 AKDP 契约从三个 ZIP 扩展为三个 ZIP 加 `zh_CN.sqlite.gz` 制品；DB schema 以 [contracts/sqlite-schema-v1.sql](../../../contracts/sqlite-schema-v1.sql) 为版本化契约。

## 后果

正面：

- 常驻内存显著下降：决策时本地实测 SQLite 模式约 104 MiB，同负载 JSON 模式约 286 MiB（降约 64%）。
- 冷路径数量级改善：进程首次敌人出场查询 794.39 ms 降至 0.48 ms，首次剧情无命中 464.16 ms 降至 12.15 ms，首次基本查询 49.49 ms 降至 1.95 ms。
- 两个后端各自 384/384 通过冻结差分，golden 快照未重录；后端互斥经系统调用追踪证实（JSON 模式零次打开 `.sqlite`，SQLite 模式零次打开原始 `.json` / `.zip`）。
- 完整 DB 磁盘占用约 289 MiB，小于旧活动数据的约 497 MiB；同步内存高水位约 14 MiB，不将整个 DB 装入内存。

负面与代价：

- 下载量上升：DB gzip 约 106 MiB，原三个 ZIP 合计约 58 MiB（约 +84%，仅 SQLite 模式承担）。
- 长扫描排队：8 个并发长扫描的最慢完成时间为 9.31 秒（旧路径 4.27 秒），这是内存优先的明确取舍。
- 部分热查询略慢（常见词命中 P95 由 1.16 ms 升至 2.26 ms）；无前缀正则查询无加速（仍需约 2.1 秒全扫）。
- 同一机器上两份游戏数据的磁盘占用上升；发行包只能内置一份备用数据的约束保持不变。

遗留事项：

- 其他平台（Windows / macOS / ARM）与正式 npm 包、Docker 渠道的实机验收在决策时尚未完成。
- AKDP 公开侧发布 DB 制品，需先交付已审查的数据编译器并固定编译器版本。
- 3.2 默认值翻转须按版本政策履行醒目提醒与迁移说明，备用数据打包策略待生产试运行结果决定。
