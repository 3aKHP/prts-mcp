> **工程档案（2026-10 · v2.8.0 – v2.8.1）**：本文整理自 2026-10-10 对 `arknights-data-pipeline`（AKDP）与 `PRTS-MCP` 开展的跨仓库剧情覆盖率静态评估报告及 Step 0/1 原始资产贯通实证，记录团队如何厘清集成战略（肉鸽）剧情的多口径分母、ASTR 指令投影丢失与管线增量缓存盲区，并通过分步发布交付 `story_supplement.json` 与 `versionId` 连字符防降级修复。

## 3. 生产管线的两处深层机制盲区

### 3.1 语法解析成功 ≠ 正文可读：`Dialog` / `PopupDialog` 尾部文本丢失

在对肉鸽未转换脚本执行 ASTR 解析预检时，所有脚本均未抛出语法异常，但抽样检查却发现 **39 篇脚本转换出的可读行数为 0**。逐文件比对原始 `.txt` 与生成的 JSON 后查明：

- 除 1 篇纯教学提示（`Tutorial`）和 10 篇纯图片引用（`Image`）外，其余 **28 篇（在 10 月 8 日完整冻结树中总计 33 篇 / 7,888 字符）全部是包含真实叙事台词的 `Dialog`（如 24 篇 RO1 月度记录 `month_chat_rogue_1_*`）与 `PopupDialog`（如 `tutorial_rogue1_b-9`）脚本**；
- Vendored ASTR 转换器仅保存 `name`、`animtext`、`multiline` 等少数指令的尾部文本，遇到 `[Dialog(head="char_171_bldsk", ...)] 台词` 时，只保留了属性字典并直接丢弃了尾部的台词正文，同时清空了 `characterStack`；
- 在 Step 1 贯通验证中，团队确认 `Dialog` 的 `head` 属性（如 `char_405_absin` → 苦艾、`char_188_helage` → 赫拉格、`char_171_bldsk` → 华法琳）可 100% 在生产端通过 `character_table.json` 解析为干员中文名，因此选定了**生产侧归一化方案**：在 AKDP 转换阶段将 `Dialog` / `PopupDialog` 内联文本投影为标准 `name` 对话行，使消费端无需修改指令解析器即可直接读取与检索。
- 此外，静态审计还定位并修复了 AKDP `summarize.py` 中的一处输入提取缺陷：ASTR 将 `Decision.options` 保存为分号分隔的单个字符串（如 `"甲;乙"`），PRTS-MCP 双端已正确将其作为单条选项处理，但 AKDP 的 `extract_chapter_text` 却对字符串执行了逐字符遍历，生成了 `【选项】甲`、`【选项】;`、`【选项】乙` 的碎片行（在 `49fef03` 中先行修复）。

### 3.2 增量缓存跳过机制与发布修订要求

静态审计同时揭示了为什么“只在 AKDP 中增加枚举并重跑流水线”无法修复既有章节或发布新目录：

1. **转换与摘要的增量跳过盲区**：
   - `story.py` 的 `convert_one` 只要发现目标 `.json` 文件已存在就会直接跳过，即使上游修正了同名 `.txt` 的正文或梗概，也不会自动重建 JSON、`storyinfo.json` 与 `wordcount.json`；
   - `summarize.py` 的 `run_summarize` 不仅只按章节 key 是否缺失来决定是否生成摘要，还会将章摘要字典强制过滤为 `story_review_table` 的 `current_keys`——如果手动为非 review 表章节（如 extra 或肉鸽）生成摘要，下一轮跑管线时就会被自动清洗删掉。
2. **打包白名单与不可变 `datarev` 修订契约**：
   - AKDP 的 `package.py` 在打包 `zh_CN.zip` 根目录索引文件时，严格按 `contract.py` 的 `STORY_INDEX_FILES` 白名单筛选；新增的顶层目录文件必须加入该白名单才会进入发布包；
   - 数据修正发布必须遵循 `prts-mcp-data/v1` 契约下的不可变修订机制（发布 `datarev-<versionId>-r<N>` 完整四资产：`zh_CN-excel.zip`、`zh_CN-levels.zip`、`zh_CN.zip` 与 `manifest.json`），绝不能通过覆盖已有 Release 资产或篡改 GitHub `Latest` 指针来充当回滚。

## 4. 静态纯函数探针发现的 `versionId` 连字符防降级缺陷

在编写纯函数探针核对 `vid = "26-10-08-04-51-28-56071834"` 的同步版本解析行为时（注：此发现来自**静态代码审查与对 `parse_data_tag` / `parse_release_suffix` 的直接函数调用探针**，而非线上运行故障报警），调研捕获了一个独立的同步层隐患：

- **现象还原**：
  - 发现新 Release 列表时，`parse_data_tag("datarev-" + vid + "-r2")` 能正常解析出元组 `(vid, 2)`，因此正常联网拉取新修订不受影响；
  - 但在解析本地已持久化的 `release_meta.json`（存储去除了前缀的 `commit_sha`）时，Python 的 `parse_release_suffix` 与 TypeScript 的对应正则仍写死要求下划线哈希分隔符 `_[0-9a-f]+`。对于 2026-10 起上游改用的全连字符格式 `26-10-08-04-51-28-56071834`（及 `-r2`），该函数返回 `None` / `null`！
- **实际影响**：一旦解析返回空，2.7.3 建立的“防降级元组比较”就会静默退化为普通字符串相等比较——若实例已安装了 `datarev-...-r2` 修复包，而远端因某种原因只返回了同源的普通 `data-...`（`r1`），客户端会误判为“字符串不同、应当更新”从而降级覆盖；缓存 ZIP 缺失时的身份保护也会一并失效。
- **独立优先处置**：团队采纳评估建议，不让该修复等待肉鸽剧情工程，而是将其作为 `2.8.0` 的必修项先行合入，使新旧两种分隔符（`_` 与 `-`）均恢复严格的 `(versionId, revision)` 元组比较。

## 5. 四种目录方案对比与分步发布兼容顺序

### 5.1 为什么选定“可选补充目录（`story_supplement.json`）”？

围绕“如何让 RO1–RO6 六个肉鸽主题在 `list_story_events`、`list_stories`、`read_activity`、`search_stories` 及角色工具中全面可达”，评估对比了四种跨仓库协同方案：

| 候选方案 | 核心做法 | 评估结论与取舍理由 |
| --- | --- | --- |
| **1. 仅 AKDP 补齐 JSON，不改目录** | 只转换肉鸽 `.txt` 放入 ZIP，`story_review_table` 不变 | ❌ **不满足发现需求**：用户不知道内部 `story_key`（如 `obt/rogue/month_chat_rogue_1_1_1`），列表、搜索与角色追踪依然全部不可达。 |
| **2. 消费端扫描 ZIP 或直接解析 `roguelike_topic_table`** | PRTS-MCP 自行遍历 ZIP 条目或双端各自解析肉鸽表 | ❌ **否决**：`Store` 抽象无枚举接口，全盘扫 ZIP 会混入 `story_variables` 且缺失活动分组与阅读顺序（入口 AVG 甚至不在 `roguelike_topic_table` 引用中）；让消费端双实现再写一套 topic 解析则会与 AKDP 的转换枚举重复维护。 |
| **3. 发布篡改后的派生 `story_review_table.json`** | AKDP 往发布的 `story_review_table.json` 中硬塞肉鸽活动条目 | ❌ **否决**：污染上游原始 Excel 表语义（且需同步修改 `zh_CN-excel.zip` 与 `zh_CN.zip` 两处的同名表），旧客户端不认识新 `entryType` 分类，且会自动触发 AKDP 对全部新增章节的强制 LLM 摘要门禁。 |
| **4. AKDP 产出可选 `story_supplement.json`，消费端合并为统一内存目录（最终选定）** | AKDP 产出符合 `prts-mcp-data/v1` 加法兼容的 `story_supplement.json`；PRTS-MCP 在构建目录与搜索索引时将其与 `story_review_table` 合并 | ✅ **选定**：原始 `story_review_table` 零污染、既有活动与密录排序不变；所有列表、全文搜索与角色追踪工具共用同一份合并目录；无长摘要的新增肉鸽章节自然走既有降级链（回退至官方短梗概或提示无梗概），不强制绑定生产端 LLM 调用成本。 |

### 5.2 生产端与消费端的分步发布兼容顺序

为了保证现网平滑过渡，团队严格按**“先收口同步身份与既定 2.8.0 特性 → 再同步交付补充目录消费端与数据修订”**的顺序分步推进：

1. **第一步：`v2.8.0`（2026-10-10）—— 干员深度数值交付 + 同步防降级先行收口**
   - 按原定范围发布 `get_operator_basic_info(action="basic" | "skills" | "stats")`、分档天赋效果与 `search(scope="skills")`，同时合入支持连字符 `versionId` 的发行身份解析修复，确保存量与升级实例具备完备的 `datarev` 修订发现与防降级能力。
2. **第二步：`v2.8.1`（2026-10-11）—— 接入 `story_supplement.json` 与目录缓存加固**
   - **双向向后兼容**：
     - **新版 `2.8.1` 客户端读取旧数据包（无 `story_supplement.json`）**：自动退回仅读取 `story_review_table.json`，行为与 `2.8.0` 完全一致；
     - **旧版 `2.x` 客户端读取新数据包（含 `story_supplement.json`）**：`prts-mcp-data/v1` 契约保持不变，旧版客户端自动忽略未知的 `story_supplement.json` 文件，原有 485 个活动与密录正常运转，且支持按已知 `story_key` 直接调用 `read_story` 读取新增的肉鸽 JSON；
     - **新版 `2.8.1` 客户端读取新数据包**：完整解锁六个 `rogue_N` 肉鸽主题，支持 `list_story_events(category="roguelike")`、章节列表排序、全文搜索与角色出场/发言统计，工具总数保持 **24 个**不变。
   - **`DirectoryStore` 搜索缓存失效修复**：评估报告专门指出，原 `DirectoryStore` 的剧情搜索缓存描述符仅检查 `story_review_table.json` 的大小与 `mtime`，若只更新 `story_supplement.json` 会导致本地目录模式缓存不失效。因此 `2.8.1` 将目录存储缓存升级为**分别跟踪每一个目录索引文件（`story_review_table.json` 与 `story_supplement.json`）的大小和时间戳**，并在数据包校验器中当补充目录存在时一并校验其引用的章节条目。
