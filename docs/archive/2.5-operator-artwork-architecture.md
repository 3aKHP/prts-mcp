# 2.5 `operator_artwork` 双后端架构设计

> **工程档案（2026-08 · v2.5.0 – v2.7.1）**：本文整理自 2.5 `operator_artwork` 工具实现交接稿（关联 Issue #85 与 `arknights-data-pipeline#1`）、2026-08-06 映射预研及 2.5.0–2.7.1 发布记录，记录干员立绘工具如何在单一 MCP 契约下融合“AKDP 本地分片资产”与“PRTS MediaWiki 实时按需拉取”两套数据源，并逐步完善增量链与安全边界。

---

## 1. 设计背景与配置默认值的演进时序

在 2.5.0 规划干员立绘与时装查询工具 `operator_artwork` 时，团队需要同时满足两类截然不同的运行场景：
1. **轻量级本地客户端（零预热诉求）**：通过 `npx` 或默认容器启动的用户希望开箱即用，不希望首次启动就下载数 GB 的全量立绘压缩包，而是“查哪个干员就实时拉哪张图”。
2. **重度创作与生产服务器（离线高可用诉求）**：常驻服务端希望将全部干员立绘与时装资产同步到本地磁盘，摆脱对 `media.prts.wiki` 外网图片链路的实时依赖，并支持获取高分辨率原图与丰富的皮肤系列元数据。

### 草案、预研与 2.5.0 首发代码的演进对照

在从早期提案走向 [`ts/v2.5.0`](https://github.com/3aKHP/PRTS-MCP/tree/ts/v2.5.0) / [`python/v2.5.0`](https://github.com/3aKHP/PRTS-MCP/tree/python/v2.5.0)（2026-08-07）正式发布的过程中，主路径定位与环境变量默认值经历了一次关键翻转：

| 阶段 | `IMAGES_ENABLED` | `LOCAL_IMAGE` | `PRTS_IMAGE_CACHE` | `ORIGINAL_IMAGE` | 当时的设计意图与调整原因 |
| --- | --- | --- | --- | --- | --- |
| **1. Issue #85 原始备忘** | 无独立开关 | 仅在线模式 | 可选缓存 | 不支持（固定 512px） | 最初仅设想通过 PRTS MediaWiki API 实时拉取 512px 缩略图，未规划本地资产包。 |
| **2. 实现交接草案** | `false` | `true` | `false` | 未独立拆分 | 草案阶段为求保守，曾计划默认关闭工具（`IMAGES_ENABLED=false`），开启后以 AKDP 本地资产为主路径（`LOCAL_IMAGE=true`），在线模式仅下载 `index.json` 做文件名映射。 |
| **3. 2026-08-06 预研（途径 B）** | — | 双后端彻底解耦 | `true`（256 MiB LRU） | — | 实测证实 `skinId` 与 MediaWiki 文件名无法可靠映射；`LOCAL_IMAGE=false` 改为不拉取 `index.json`，直接查询 PRTS MediaWiki 并默认启用 256 MiB 内存缓存。 |
| **4. `v2.5.0` 首发正式代码** | **`true`** | **`false`** | **`true`** | **`false`** | 双路径均通过端到端验证后，`v2.5.0` 首发即默认开启 `IMAGES_ENABLED=true`（工具数 23 → 24），默认采用零磁盘预热的 `LOCAL_IMAGE=false` + `PRTS_IMAGE_CACHE=true`；重度部署按需显式开启 `LOCAL_IMAGE=true`（及可选 `ORIGINAL_IMAGE=true`）。 |

这一最终默认值组合（见 `ts/v2.5.0:ts/src/config.ts` 的 `loadConfig()`）一直延续至 3.x：普通用户无需配置即可使用第 24 个工具，而容器与离线环境只需切换环境变量即可无缝切入全量本地资产模式。

## 2. 统一工具契约与不透明 `artwork_id`

无论底层处于哪种图片模式，`operator_artwork` 对外暴露完全一致的签名：

```text
operator_artwork(
  operator_name: string,
  action: "list" | "get",
  artwork_id?: string,
  variant?: "original" | "large" | "preview"
)
```

### 2.1 为什么强制拆分为 `list` → `get` 两步调用？

- **`action="list"`（仅元数据，零图片字节）**：一名干员通常包含精英零、精英二、升变形态及多套时装立绘。若单次调用返回全部图片的 Base64，会瞬间撑爆客户端内存与模型上下文。因此 `list` 仅返回有界文本摘要与 `structuredContent` 元数据（含可用变体的宽高与字节数），帮助模型按需挑选。
- **`action="get"`（单次至多一张 `ImageContent`）**：客户端回传 `list` 给出的 `artwork_id` 与可选 `variant`（默认 `large`，最大边长 1024px；`preview` 最大边长 256px；`original` 为原始分辨率），服务端返回一段来源说明文本与**至多一张**纯 Base64 编码的 PNG 图片（`mimeType: "image/png"`，不含 `data:image/png;base64,` 前缀）。任何查找失败、下载越界或校验错误均退化为纯文本提示，绝不返回残缺图片或半成品 `structuredContent`。

### 2.2 不透明令牌（Opaque Token）契约

`artwork_id` 被定义为**客户端不可自行构造、不可跨模式混用**的不透明令牌，两个后端各自采用最契合自身数据源的内部表示：

| 模式 | `artwork_id` 内部表示 | 代表性示例 | 解析与校验方式 |
| --- | --- | --- | --- |
| **本地资产模式（`LOCAL_IMAGE=true`）** | 游戏表 `skinId`（与 AKDP `index.json` 的键一致） | `char_002_amiya#1`、`char_002_amiya#2`、`char_1001_amiya2#2`、`char_002_amiya@epoque#4` | 查本地已激活代际的 `index.json` 获取相对文件路径 |
| **在线按需模式（`LOCAL_IMAGE=false`）** | 规范化的 PRTS MediaWiki 文件标题 | `立绘_阿米娅_1.png`、`立绘_阿米娅_2.png`、`立绘_阿米娅(近卫)_2.png`、`立绘_阿米娅_skin1.png` | 经 MediaWiki `imageinfo` 解析缩略图 URL 并执行安全下载 |

## 3. 为什么放弃“跨模式 ID 映射”，改走双路径完全解耦？

在交接草案最初的设计中，曾希望让 `LOCAL_IMAGE=false` 模式在启动时也只下载一份约 1.1 MB 的 AKDP `index.json`，在 `list` 时复用 `skin_table.json` 生成标签，在 `get` 时将 `skinId` 程序化翻译为 PRTS MediaWiki 文件名。

然而 2026-08-06 的技术预研（Spike）证实**两套命名体系之间不存在可靠的程序化映射函数**：

1. **基础立绘可映射，但时装编号体系完全异构**：
   - 基础立绘满足 `char_002_amiya#1` → `立绘_阿米娅_1.png`、`char_002_amiya#2` → `立绘_阿米娅_2.png` 的规则；
   - 但时装在游戏表 `skin_table.json` 中按品牌主题系列独立编号（如阿米娅的“见习联结者”为 `char_002_amiya@epoque#4`、“报童”为 `char_002_amiya@winter#1`），而 PRTS MediaWiki 上的立绘文件则按时装实装上线顺序统一命名为 `立绘_阿米娅_skin1.png`、`立绘_阿米娅_skin2.png`。
2. **双端均缺少桥接元数据**：
   - `skin_table.json` 中没有对应 PRTS Wiki `_skinN` 序号的全局排序字段（同一干员的多套皮肤在不同品牌系列下也没有单调递增的序号）；
   - 查询 PRTS MediaWiki 的 `prop=imageinfo&iiprop=extmetadata` 时，返回的文件扩展元数据为空，无法从 Wiki 侧反查对应的游戏内 `skinId`。

### 转向“途径 B（双路径完全解耦）”的收益与代价

基于预研实证，架构果断否决了脆弱的启发式猜测映射，改为**两条路径完全解耦（途径 B）**：`LOCAL_IMAGE=false` 启动时不下载任何 AKDP 索引，直接通过 MediaWiki `allimages` 与词条 `CharinfoV2` 模板完成发现与命名。

这一决策消除了时装错配风险，但也让项目明确承担了**双路径并行维护的工程成本**：
- **两套发现与标签组装逻辑**：本地模式通过 `index.json` 关联 `skin_table.json`（由 `displaySkin.skinName` 与 `skinGroupId` 生成标签，并在 2.5.0 首发验证了 1,362 张立绘条目）；在线模式则需通过 `allimages`（前缀 `立绘_<干员名>_`，在 2.5.0 中专门修复了超过 50 张图片时的 `aifrom` 续页截断问题，并跳过 `_Nb` 基建小人）结合 `CharinfoV2` 模板的 `时装1名称`、`时装2名称` 组装标签。
- **两套形态别名与归属校验**：后续针对阿米娅升变形态（近卫/医疗）与跨干员 Token 校验的每次加固，都必须在本地 `skinId` 与 MediaWiki 文件名两套规则上同步实现并保持行为同构。

## 4. AKDP 生产/消费契约与增量链演进（`LOCAL_IMAGE=true`）

### 4.1 生产端与消费端的职责边界及 Manifest/Index 衔接

为了避免在 MCP 服务端引入重型图像处理依赖（如 `Pillow` 或 `sharp`），立绘管线采用了严格的**生产/消费分离架构**：

- **生产端（`3aKHP/arknights-data-pipeline`）**：负责从解包资产中提取立绘，预渲染 `original`（原尺寸）、`large`（最大边长 1024px）、`preview`（最大边长 256px）三档 PNG，按基础立绘（`chararts`）与时装（`skinpack`）打包为基线分片 ZIP（发布在 `images-baseline-<ver>` Release）及增量包 `images-delta-<ver>.zip`（发布在 `images-<ver>` Release），并生成权威索引 `index.json`。
- **消费端（PRTS-MCP）**：不做任何实时图像缩放，仅负责按 `images-` 前缀发现 Release（与 `data-*` Release 隔离，避免 GitHub `/releases/latest` 指向图片发布导致游戏表同步停滞）、按需拉取分片、校验 `sha256`、原子激活代际目录并对外提供查询。

两端通过冻结 Schema（`akdp-images/v1`）的 `index.json` 与消费端本地状态文件 `.images_meta.json` 衔接：

1. 生产端发布的权威索引 `index.json`（结构示意）：

```json
{
  "schemaVersion": "akdp-images/v1",
  "baselineVersion": "20260801-a1b2c3d",
  "currentVersion": "20260807-e4f5g6h",
  "shards": {
    "chararts-large": "chararts-large.zip",
    "chararts-preview": "chararts-preview.zip",
    "skinpack-large": "skinpack-large.zip",
    "skinpack-preview": "skinpack-preview.zip",
    "chararts-original": "chararts-original.zip",
    "skinpack-original": "skinpack-original.zip"
  },
  "artworks": {
    "char_002_amiya#2": {
      "kind": "base",
      "shard": "chararts",
      "sinceVersion": "20260801-a1b2c3d",
      "large": { "file": "large/char_002_amiya_2.png", "w": 1024, "h": 1024, "bytes": 845120, "sha256": "..." },
      "preview": { "file": "preview/char_002_amiya_2.png", "w": 256, "h": 256, "bytes": 76400, "sha256": "..." },
      "original": { "file": "original/char_002_amiya_2.png", "w": 2048, "h": 2048, "bytes": 2910400, "sha256": "..." }
    }
  }
}

```

2. 消费端激活后落盘的 `.images_meta.json`（结构示意）：

```json
{
  "schemaVersion": "akdp-images/v1",
  "baselineVersion": "20260801-a1b2c3d",
  "currentVersion": "20260807-e4f5g6h",
  "shardsSynced": ["chararts-large", "chararts-preview", "skinpack-large", "skinpack-preview"],
  "generation_root": ".releases/9f86d081884c7d65-3b9a..."
}
```

### 4.2 基线分片、原图开关与增量链（Delta Chain）的演进修复

消费端根据 `ORIGINAL_IMAGE` 环境变量决定需要同步的分片集合 `shardsSynced`：默认（`ORIGINAL_IMAGE=false`）仅同步 4 个 `large`/`preview` 分片（约 1.5 GB）；当开启 `ORIGINAL_IMAGE=true` 时，额外同步 `chararts-original` 与 `skinpack-original` 两个原图分片（总计约 5.1 GB）。由于 `shardsSynced` 记录在 `.images_meta.json` 中，用户事后开启 `ORIGINAL_IMAGE=true` 时，同步器会检测到分片集合变化并自动触发补齐重建。

在增量包（Delta）的应用逻辑上，该子系统经历了从“单增量覆盖”到“完整增量链重放”的重要演进：

1. **2.5.0 首发实现（仅叠加最新单个 Delta）**：
   - 如交接稿 §2.1 及 `ts/v2.5.0:ts/src/data/imagesSync.ts` 所示，2.5.0 的同步器在下载基线分片（或复制同 `baselineVersion` 的上一个代际目录）后，只下载并解压**最新那一个** `images-delta-<currentVersion>.zip`，且未在激活前逐个核对所需变体 PNG 的 `sha256`。
2. **2.5.1（2026-08-07）：补齐激活前逐变体 `sha256` 校验**：
   - 在将暂存目录（`.releases/.<gen>.tmp`）重命名为正式代际目录前，同步器新增了对 `index.json` 中每个干员所需变体 PNG 的存在性与 `sha256` 摘要核对；任一必需 PNG 缺失或哈希不匹配即中止激活并保留旧代际。
3. **2.7.1（#179）：修复多增量断裂，改为按序应用完整增量链**：
   - **暴露的缺陷**：当 AKDP 在同一 `baselineVersion` 周期内连续发布了两个及以上非空增量（例如 `v1`、`v2`）时，由于每个 `images-delta-<v>.zip` 仅包含该次提交新增或修改的 PNG，新安装的 `LOCAL_IMAGE=true` 实例或跨版本升级实例若只下载基线 + 最新 `v2` 增量，就会缺失 `v1` 增量中的立绘文件，导致在耗费 1.5 GB（或 5.1 GB）流量下完基线后，在 2.5.1 引入的 `sha256` 校验处必然失败（旧单元测试因使用空 `artworks` mock 字典而未能捕获此问题）。
   - **修复机制**：2.7.1 将同步器改造为枚举并按版本顺序重放满足 `baselineVersion < v <= currentVersion` 的**整条 `images-*` 增量链**；同时持续分页拉取 GitHub Releases 直至覆盖增量链起点（避免单页 100 条上限截断历史增量），以 `index.json` 的 `currentVersion` 为权威源交叉核对最新 tag，并在开始下载 GB 级基线分片前预先检查整条增量链资产是否齐全（若增量链断裂则立即失败，不浪费带宽）；复用已有代际的快速路径则仅按序叠加晚于自身 `currentVersion` 的后续增量。

## 5. 在线按需模式的安全边界与画质/带宽取舍（`LOCAL_IMAGE=false`）

在默认的 `LOCAL_IMAGE=false` 模式下，每一次 `action="get"` 都会触发服务端向外部网络请求图片字节。为防止服务端被诱导发起 SSRF 攻击或被超大畸形文件耗尽内存，2.5.0 完整落地了 Issue #85 制定的多层防御边界：

- **缩略图策略与禁用 `original` 变体**：服务端通过 MediaWiki `action=query&prop=imageinfo&iiprop=url&iiurlwidth=1024`（`large`）或 `256`（`preview`）获取由 PRTS CDN 预缩放的缩略图地址。由于 PRTS 上的原始立绘常超过 2–4 MiB，在线模式显式拒绝 `variant="original"` 并返回清晰提示，以此在 1024px 实用画质与单次 MCP 载荷体积之间取得平衡。
- **五重下载安全校验（`download_image_safe`）**：
  1. **域名白名单**：仅允许请求 `media.prts.wiki`，若遇 HTTP 重定向，对每一跳目标 URL 重新校验主机名白名单；
  2. **流式有界读取与 1 MiB 硬上限**：边读取响应流边累加字节数，一旦解码后载荷超过 **1 MiB（1,048,576 字节）** 立即中止连接并丢弃缓冲；
  3. **HTTP `Content-Type` 校验**：响应头必须匹配受支持的图像 MIME 类型；
  4. **文件头魔数签名（Magic Bytes）验证**：核对字节流开头的 PNG / JPEG / WebP 魔数签名，杜绝伪装成图片的 HTML 错误页或恶意载荷混入 `ImageContent`；
  5. **256 MiB 进程内 LRU 缓存（`PRTS_IMAGE_CACHE=true`）**：校验通过的图片字节按大小计入进程内 256 MiB 上限的 LRU 缓存，避免同一创作会话反复请求外网。

| 版本 | 发布日期 | 核心加固与架构演进 |
| --- | --- | --- |
| **`v2.5.0`** | 2026-08-07 | 首发 `operator_artwork`（默认 `IMAGES_ENABLED=true, LOCAL_IMAGE=false, PRTS_IMAGE_CACHE=true`）；确立不透明 `artwork_id`、双后端解耦（途径 B）、MediaWiki `allimages` `aifrom` 续页与 `data-*` / `images-*` tag 前缀隔离发现。 |
| **`v2.5.1`** | 2026-08-07 | 本地模式（`LOCAL_IMAGE=true`）在激活新代际前新增对每个所需变体 PNG 的文件存在性与 `sha256` 校验，阻止缺失或损坏的分片静默激活。 |

| **`v2.7.0`** | 2026-08-15 | **路径包含检查（realpath）与模块解耦（#169 / P3.B）**：将 TypeScript 本地模式读取 PNG 时的路径包含检查从纯词法相对路径升级为 `realpathSync` 符号链接解析（对齐 Python 原有的 `Path.resolve()`，防止代际目录内符号链接逃逸读取宿主机文件）；将立绘模块拆分为 `artworkLocal`、`artworkMediawiki`、`artworkFormat` 并把 `imagesSync` 迁入独立 `sync/` 层；同时将 Python `_download_large` 对齐为每次镜像尝试 30 分钟的总期限，并补充皮肤品牌、系列、获取途径等丰富展示元数据。 |
| **`v2.7.1`** | 2026-08-18 | **完整 AKDP 增量链重放（#179）**：修复基线后存在多个非空增量 Release 时仅应用最新单个 delta 导致校验失败的缺陷，改为分页发现并按序重放 `baselineVersion < v <= currentVersion` 的全部增量包。 |
