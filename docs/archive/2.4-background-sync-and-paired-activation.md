# 2.4 常驻后台同步、成对代际激活与共享卷恢复

> **工程档案（2026-07 – 2026-10 · v2.4.0 – v2.8.0）**：本文整理自 2.4.0 自动同步 PR（`#78`）、`ts/v2.4.0` 与 `python/v2.4.0` 源码实现及 2.5–2.8 后续修复记录，梳理数据同步子系统如何从“启动时单次覆盖解压”演进为支持周期热更新、跨数据集原子成对激活（Paired Activation）与跨进程共享卷锁的状态机。现行运维说明请参阅 [`docs/admin/data-and-sync.md`](../admin/data-and-sync.md)。

## 1. 演进动机：为什么不能“下载后直接覆盖解压”？

在 2.4.0 之前，PRTS-MCP 仅在进程启动时触发一次后台同步，且对需要解压的 `zh_CN-excel.zip`（`gamedata`）与 `zh_CN-levels.zip`（`gamedata-levels`）采用“下载 ZIP 后直接解压覆盖目标目录”的方式。当 2.4.0 引入贯穿进程生命周期的周期自动同步（默认 `PRTS_AUTO_SYNC_INTERVAL_SECONDS=3600`）时，原有的直接覆盖模型暴露出三个严重隐患：

1. **解压中途的半成品暴露与崩溃残留**：
   - `zh_CN-excel.zip` 与 `zh_CN-levels.zip` 包含数十个大型表格与数千个关卡 JSON。若在运行期直接向活跃目录原地解压，正在并发执行的 MCP 工具请求会读到写了一半的目录树；
   - 若进程在“ZIP 已下载并更新了 `release_meta.json`，但解压中途崩溃或被强杀”，下次启动虽会检查必需文件是否齐全，却无法据此确认整棵目录是否已更新完成。若必需文件仍在、新旧内容混杂，且远端 tag 未变，就可能跳过重新解压，继续使用混代数据。
2. **`excel` 与 `levels` 混代（Cross-Generation Skew）**：
   - `get_enemy_info(name, stage_id)` 与 `get_stage_enemies(stage_id)` 需要同时关联 `excel`（`stage_table.json`、`enemy_handbook_table.json`）与 `levels`（`enemy_database.json` 及关卡波次 JSON）。
   - 如果 `excel` 先完成更新而 `levels` 下载失败或尚在解压，工具就会用新版 `stage_table` 去查旧版 `levels` 目录，导致新活动关卡找不到对应波次文件或敌人属性错位。
3. **共享数据卷上的多进程并发踩踏**：
   - 在 Docker 命名卷或宿主机共享数据目录场景下，多个容器或 Python / TypeScript 实例可能同时触发周期同步，争相写同一个 `.tmp` 文件或同时清理代际目录。

## 2. 暂存、校验与成对代际激活（Paired Activation）

为彻底消除原地覆盖与混代问题，[`ts/v2.4.0`](https://github.com/3aKHP/PRTS-MCP/tree/ts/v2.4.0) 与 [`python/v2.4.0`](https://github.com/3aKHP/PRTS-MCP/tree/python/v2.4.0) 将“压缩包已下载”与“解压树已激活”拆分为两个独立持久化的状态，并引入**单数据集代际树 + 跨数据集权威配对指针**的双层发布机制。

### 2.1 状态流转与目录布局

```text
1. 发现候选 Release ──▶ 2. 下载并校验 ZIP（更新 archives/release_meta.json）
                           │
3. 解压至隔离暂存目录 .releases/.<sha16>-<uuid>.tmp/ 并校验必需文件
                           │
4. 原子重命名为 .releases/<sha16>-<uuid>/ 并写入 archives/extract_meta.json
                           │
5. 当 excel 与 levels 的 extract_meta.commit_sha 一致且文件齐全时
   ──▶ 原子更新共同父目录的权威指针 .gamedata_pair.json
                           │
6. 下一次工具调用检测到激活签名变化 ──▶ 触发领域缓存失效并读取新代际
```

在磁盘上，三份元数据文件各司其职（最小结构示例如下）：

1. `gamedata/archives/release_meta.json`（记录已下载的 ZIP 归档状态）：

```json
{
  "repo": "3aKHP/ArknightsGameData",
  "branch": "releases",
  "commit_sha": "a1b2c3d4...",
  "fetched_at": "2026-07-29T06:00:00.000Z",
  "files": ["zh_CN-excel.zip"]
}
```

2. `gamedata/archives/extract_meta.json`（记录单数据集已解压就绪的代际目录）：

```json
{
  "commit_sha": "a1b2c3d4...",
  "data_root": ".releases/9f86d081884c7d65-4e2a..."
}
```

3. `<data_root>/.gamedata_pair.json`（跨数据集同代成对激活的权威指针）：

```json
{
  "commit_sha": "a1b2c3d4...",
  "excel_data_root": ".releases/9f86d081884c7d65-4e2a...",
  "levels_data_root": ".releases/9f86d081884c7d65-8b1c..."
}
```

### 2.2 成对指针、工具快照与失败回退的关系

- **查询侧单次调用一致性（`withActivationSnapshot`）**：工具执行入口在调用开始时捕获当前的激活签名（由 `.gamedata_pair.json` 与两份 `extract_meta.json` 的 `ino`、`size`、`mtime`、`ctime` 组成）并固定 `Config` 快照，保证同一次工具调用内部即使遇上后台切换代际，也不会在前半段读旧表、后半段读新表。
- **单边失败时继续服务旧代**：在 `syncReleaseArchivePair` 中，如果 `excel` 升级到了新 SHA `B`，而 `levels` 因网络波动停留在旧 SHA `A`（返回 `offline_fallback`），由于 `excelMeta.commitSha !== levelsMeta.commitSha`，**`.gamedata_pair.json` 不会更新**。此时 `loadConfig()` 通过 `activatedPair()` 仍解析到指向旧代 `A` 的 `.releases/<gen-A>/` 目录，且旧代目录因受 24 小时保留期（`RELEASE_RETENTION_MS = 24h`）及配对 `utimes` 刷新保护而不会被立刻删除，线上查询继续无缝读取完整的旧代 `A` 配对。

## 3. 共享卷跨进程锁协议（Owner · 心跳 · 租约 · 接管）

由于同一个数据卷可能被 Python 与 TypeScript 进程（或多容器副本）挂载，同步器采用基于标准文件系统原子 `mkdir` 的跨语言目录锁协议，按职责划分为两级锁名：
- **配对协调锁**：共同父目录下的 `.gamedata-pair.lock`；
- **单数据集激活锁与下载锁**：各 `archives/` 目录下的 `.activation.lock` 与 `.release.lock`（以及 2.5 引入的 `.images.lock`）。

锁顺序严格固定为 `pair lock → excel activation lock → excel release lock`（释放后再获取 `levels activation lock → levels release lock`），杜绝跨进程死锁。

### 锁生命周期与参数设计（`withArchiveActivationLock`）

| 机制 | 2.4.0 固定参数 | 行为规则 |
| --- | --- | --- |
| **原子获取与 Owner 登记** | 轮询间隔 `50ms`，总等待上限 `120s` | 调用 `mkdir(lock)`；成功后立即写入 `lock/owner`（随机 32 位十六进制 UUID）。若写入 `owner` 失败，立即回滚删除锁目录。同时拒绝符号链接形式的锁路径。 |
| **后台心跳续租（Heartbeat）** | 每 `60s`（`ACTIVATION_LOCK_HEARTBEAT_MS`） | 持有锁期间，后台定时器（TS 调用 `.unref()`，Python 使用守护线程）每 60 秒读取一次 `lock/owner`：仅当内容仍等于自身 `owner` 时，通过 `utimes` 刷新 `owner` 文件的 `mtime`，防止慢速下载或大包解压被误判为死锁。 |
| **无主宽限与陈旧锁接管（Takeover）** | 无主宽限 `10s`，有主陈旧阈值 `30min` | 竞争者遇到 `EEXIST` 时检查 `lock/owner`：若 `owner` 文件不存在且锁目录创建已超 `10s`（进程在 `mkdir` 后、写 `owner` 前崩溃），或 `owner` 文件 `mtime` 距今已超 `30min`（持有者崩溃失联），竞争者先将旧锁原子重命名为 `.stale-<uuid>` 隔离再递归删除，随后重新进入获取循环。 |
| **安全释放（Owner Verification）** | `finally` 块核验 | 退出临界区前停止心跳，重新读取 `lock/owner`；**仅当文件内容仍等于本实例 `owner` 时才删除锁目录**，确保因极端卡顿被判定陈旧的旧持有者苏醒后，绝不会误删接班者的新锁。 |

*(注：翻阅 `feat/v2.4.0-auto-sync`（PR `#78`）的提交历史可见，当时直接确立了这套跨平台、跨 Python/TypeScript 零额外依赖的目录 + `owner` 租约文件方案，代码库与提交记录中未留存针对 `flock`/`fcntl` 等操作系统级文件锁的书面对比报告。)*

## 4. 异常场景恢复与测试实证

在 2.4.0 中，同步状态机针对四类典型故障建立了自愈路径，并由双端测试套件（`ts/tests/sync.test.ts` 与 `python/tests/test_sync_release.py`）逐一锁定：

1. **ZIP 下载成功但解压中途失败或进程崩溃**：
   - **恢复逻辑**：`syncReleaseArchiveLocked` 判定是否需要解压的条件为 `shouldExtract = releaseResult.status === "updated" || !filesOk || extractedSha === null || extractedSha !== releaseResult.commitSha`。若上一轮下载了新 ZIP（`release_meta.json` 已更新），但解压抛错或中断（`extract_meta.json` 未更新或目标目录缺必需文件），下一轮周期检查即使发现远端 Release 未变（`releaseResult.status === "up_to_date"`），也会因为 `extractedSha !== releaseResult.commitSha` 或 `!filesOk` 自动触发重新暂存解压，无需重新下载 ZIP。
   - **测试实例**：`test("syncReleaseArchive retries activation after extraction failure")`（模拟首次解压时损坏 ZIP，恢复正常 ZIP 后无需发版变更即完成重提激活）与 `test("syncReleaseArchive reports updated after offline activation recovery")`（断网状态下直接基于本地已缓存的未激活 ZIP 完成解压并报告 `updated`）。
2. **解压或下载失败时的回退保护**：
   - **恢复逻辑**：暂存解压在独立的 `.releases/.<gen>.tmp` 中进行，一旦缺少必需条目或遇到非法路径（如 `..`），立即清理 `.tmp` 目录；只要旧的 `activeRoot` 文件仍然完整，函数返回 `offline_fallback` 而非 `no_data`。
3. **配对元数据缺失或从旧版升级（Legacy Bootstrap）**：
   - **恢复逻辑**：`initializeGamedataPair` 在首次运行找不到 `.gamedata_pair.json` 时，自动检查现有 `excel` 与 `levels` 的已激活目录并补建初始配对指针，实现从 2.3.x 旧数据卷的无感平滑升级。
4. **单边更新时的配对保持**：
   - **测试实例**：`test("pair manifest switches only after both archives share one SHA")` 验证了当 `excel` 升至 `sha-new` 而 `levels` 仍为 `sha-old` 时，`.gamedata_pair.json` 保持指向 `sha-old`，直至 `levels` 也同步到 `sha-new` 后才一次性切换配对指针。

## 5. 区分 2.4 首发能力与 2.5–2.8 后续增强

阅读现行代码时需注意：**今天完整的同步状态机并非在 2.4.0 一次性建成**，而是在 2.4.0 奠定骨架后，历经多个小版本逐步补齐了上游切换、幂等防抖与防降级能力：

| 版本 | 发布日期 | 同步子系统的实际演进内容 |
| --- | --- | --- |
| **`v2.4.0`（首发基线）** | 2026-07-29 | 引入周期自动同步（`PRTS_AUTO_SYNC_INTERVAL_SECONDS`）、`.releases/<gen>/` 暂存与代际激活、`.gamedata_pair.json` 成对激活指针，以及带心跳续租的共享卷目录锁。此时上游仍指向旧仓库（`ArknightsGameData` / `ArknightsStoryJson`），使用 `/releases/latest` 端点与 `upstream-` tag 前缀，尚无 `manifest.json` 校验。 |
| **`v2.5.0`** | 2026-08-07 | **切换至自托管 `3aKHP/arknights-data-pipeline` 并引入 Manifest 校验**：发现机制从 `/releases/latest` 改为拉取 Release 列表并按 `data-` / `images-` tag 前缀过滤（防止图片 Release 成为 Latest 后阻塞数据更新）；新增 `verifyReleaseManifest`（核对 `contractVersion: "prts-mcp-data/v1"`、`source.versionId` 以及各 ZIP 资产的字节大小与 `sha256`）。 |
| **`v2.5.1`** | 2026-08-07 | **区分 Manifest 真实缺失与镜像故障 + 抑制无效密集重试**：引入 `AssetNotFoundError`，仅当直连 GitHub 明确返回 HTTP 404 时才视为早于 Manifest 机制的旧版 Release 并放行兼容，防止镜像代理的通用 404 静默跳过校验；同时修复当 `excel` 与 `levels` 均已最新但历史 `commit_sha` 元数据不一致时错误触发 30s/120s/600s 密集重试的问题。 |
| **`v2.6.2`（`#152` / `#154`）** | 2026-08-12 | **配对指针幂等写入（消除周期性误失效）**：修复了 2.4.0 的一个隐蔽缺陷——在 2.4.0 中，`syncReleaseArchivePair` 每小时执行完周期检查后，即便 `excel` 与 `levels` 均未变化（`up_to_date`），仍会无条件重写一次 `.gamedata_pair.json`，导致文件 `ino`/`mtime` 改变，进而每小时误触发一次全量 GameData 内存缓存清空与重建。2.6.2 在 `saveGamedataPair` 中加入比对守卫：当 `commit_sha` 及解析后的 `excelRoot`/`levelsRoot` 均未变化时直接短路返回，确保只有真实代际变化或配对损坏时才更新文件并失效缓存。 |
| **`v2.7.0`（`P2` / `P4.B`）** | 2026-08-15 | 将同步状态机从 `data/sync` 剥离至独立顶层 `sync/` 层（`transport`、`release_discovery`、`release_activation`、`release`、`gamedata_pair`）；统一双端 `GITHUB_MIRRORS` 末尾斜杠与空白归一化，并将锁等待超时规范化为具名异常 `ActivationLockTimeoutError`。 |
| **`v2.7.3`** | 2026-09-05 | 支持 `datarev-<versionId>-r<N>` 修订发布命名空间，按 `(versionId, revision)` 比较数据发布身份，先比较源版本标识，再比较同一源版本的修订号，防止修订包被旧数据覆盖。 |
| **`v2.8.0`** | 2026-10-10 | 修复已存发布身份的解析，使其兼容连字符形式的 `versionId`（如 `26-10-08-04-51-28-56071834`）。此前该格式会退回普通字符串比较，绕过修订号防降级检查；修复后恢复 `(versionId, revision)` 比较。正常发布发现与更新原已兼容该格式。 |
