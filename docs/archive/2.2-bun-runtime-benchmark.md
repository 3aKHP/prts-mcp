# 2.x TypeScript 运行时演进：Node.js → Bun 基准测试

> **工程档案（2026-07 · v2.0.2 – v2.2.0）**：本文整理自 2026-07-04 的 Bun 运行时迁移基准测试与分阶段实施规划，完整保留了当时评估 `Node.js v22.22.3` 与 `Bun 1.3.14` 的测量条件、有利与不利结果，以及为何采取“先可选就绪、再切默认运行时、保留 Node 启动桥与 npm OIDC 发布链”的工程决策。在 3.0 迁移至原生 Rust 后，当时的 `TS 2.8.1 + Bun 1.3.14` 成为了 3.0 契约对照与性能评测的基准（Oracle）。

---

## 1. 测试背景与实验方法

在 2.0 完成工具面收敛与双通道重构后，TypeScript 实现承担了主要的常驻 Streamable HTTP 服务角色。为了评估将 TypeScript 运行时从 Node.js 迁移至 Bun 的真实收益与潜在代价，我们在 2026-07-04 对 **源码依赖安装、Docker 镜像构建与冷启动、携带 76 MiB 随包数据的 npm Tarball 安装，以及常驻 HTTP 服务的工具调用延迟** 开展了对照实测。

### 统一实验环境与控制条件

- **硬件与文件系统**：Windows 工作站上的 WSL2 Ubuntu 24.04.4 LTS；所有安装与运行时测试均在原生 WSL `ext4` 文件系统（`/tmp` 下的独立临时目录）中执行，刻意避开 `/mnt/*` 跨系统挂载盘，以消除 Windows/WSL 文件系统桥接的 I/O 干扰。
- **对比工具链版本**：`Node.js v22.22.3` + `npm 10.9.8` vs. `Bun 1.3.14`；容器引擎为 `Docker 29.2.1`。
- **数据集与网络隔离控制**：将随包 `gamedata` 与最新公开的 `3aKHP/ArknightsStoryJson` `zh_CN.zip` 拷入包内 `data/` 目录；在常驻延迟测试中，显式将 `GAMEDATA_PATH` 指向空临时目录以禁用启动时后台自动同步，确保两侧 100% 稳定命中相同的本地随包只读数据。
- **样本口径的留存边界（缺失项标为待查）**：原始基准记录仅在发布态 Tarball 安装一轮注明“5 次独立运行取中位数”；源码依赖安装与 Docker 构建/冷启动两轮未记录重复运行次数，常驻延迟各场景亦未留存具体调用次数与测量脚本——以上缺失项均标为待查，本文按原始记录如实呈现，不作推测性补全。

## 2. 逐场景实测数据（含测量口径与不利结果）

### 2.1 源码树依赖安装与构建（包管理器全局缓存已预热 + 干净工作目录）

| 测试项 | `npm` / `Node.js v22.22.3` | `Bun 1.3.14` | 测量口径与结果解读 |
| --- | ---: | ---: | --- |
| **干净源码树安装耗时** | `2.183s`（峰值 RSS `~204 MiB`） | `0.146s`（峰值 RSS `~17 MiB`） | 全局缓存已预热、目标目录干净；Bun 安装速度快约 **15×**，峰值内存降低超 **90%**。 |
| **`node_modules` 磁盘占用** | `64 MiB` | `64 MiB` | 源码依赖树落盘体积持平，无磁盘节省。 |
| **锁文件体积** | `64 KiB`（`package-lock.json`） | `40 KiB`（`bun.lock`） | Bun 锁文件小约 **38%**。 |
| **TypeScript 编译构建（`tsc`）** | `2.104s` | `1.941s` | 均调用 `tsc` 编译，构建提速仅约 **8%**（核心收益在安装而非编译）。 |

### 2.2 携带 76 MiB 随包数据的发布态 Tarball 安装（5 次独立运行取中位数）

为模拟用户安装 CI 发布的完整 `prts-mcp-ts` 包，先构建 `dist/`、填入 `data/gamedata` 与 `data/storyjson/zh_CN.zip`（打包前 `data/` 目录 `76 MiB`），执行 `npm pack` 产出 **`49 MiB` 的 `.tgz` 归档**（安装后包本体目录固定为 `77 MiB`），随后在全新的空项目中分别执行 5 次安装并取中位数：

| 测试项 | `npm install <.tgz>` | `bun add <.tgz>` | 结果解读（含磁盘占用劣势） |
| --- | ---: | ---: | --- |
| **安装耗时（5 次中位数）** | `4.061s` | `0.594s` | 即便包含 49 MiB 压缩包解压，Bun 仍快约 **6.8×**。 |
| **安装峰值 RSS** | `~312 MiB` | `~203 MiB` | 峰值内存降低约 **35%**。 |
| **已安装 `prts-mcp-ts` 包目录体积** | `77 MiB` | `77 MiB` | 包内编译产物与随包数据完全相同。 |
| **包外额外 `node_modules` 体积** | `26 MiB` | **`56 MiB`（劣势）** | Bun 的依赖布局在包外多占用了约 **30 MiB**。 |
| **全新项目总磁盘占用** | `103 MiB` | **`133 MiB`（劣势）** | **不利结果**：对于携带大体积随包数据的 Tarball，Bun 并未节省磁盘空间，反而使全新安装目录增大约 **30 MiB（+29%）**。 |

### 2.3 Docker 镜像构建与冷启动（`node:24-alpine` vs. `oven/bun:1.3.14-alpine`）

在基础镜像均已拉取缓存的前提下，执行无缓存镜像构建（`docker build --no-cache`）并测量容器启动至 `/health` 首次返回 200 的耗时与初始内存：

| 测试项 | Node 镜像路径（`node:24-alpine`） | Bun 镜像路径（`oven/bun:1.3.14-alpine`） | 结果解读（含初始 RSS 对比） |
| --- | ---: | ---: | --- |
| **无缓存镜像构建耗时** | `19.602s` | `16.569s` | 构建快约 **15%**。 |
| **最终镜像体积** | `~73.9 MiB` | `~56.1 MiB` | 镜像体积缩小约 **24%（−17.8 MiB）**。 |
| **容器启动至 `/health` 就绪** | `1.268s` | `1.036s` | 冷启动快约 **18%**。 |
| **`/health` 就绪后空载初始 RSS** | `~53 MiB` | **`~59 MiB`（略高）** | **不利结果**：仅启动至 `/health` 的空载冒烟下，Bun 容器的初始常驻内存比 Node 略高约 **6 MiB**。 |

### 2.4 常驻 HTTP MCP 服务调用延迟（复用单会话连续调用，`p50 / p95 / p99`）

模拟 systemd 托管的常驻生产 HTTP 服务，由同一客户端复用单条 MCP 会话执行主混合负载运行（`tools/list`、`get_operator_basic_info`、`list_story_events`）及 `read_story` 专项运行（读取 `activities/act49side/level_act49side_01_beg`）：

| 调用场景 | Node.js (`p50 / p95 / p99`) | Bun 1.3.14 (`p50 / p95 / p99`) | 结果解读（含尾延迟波动） |
| --- | ---: | ---: | --- |
| `tools/list` | `3.78 / 5.41 / 6.46 ms` | `3.69 / 8.09 / 10.84 ms` | `p50` 持平（`3.69ms` vs `3.78ms`），但 **Bun 在该次运行中的 `p95`（`8.09ms`）与 `p99`（`10.84ms`）尾延迟弱于 Node**。 |
| `get_operator_basic_info` | `2.57 / 4.93 / 7.78 ms` | `2.24 / 4.55 / 9.74 ms` | 内存 JSON 表查询延迟接近：Bun 的 `p50`/`p95` 略优，而 **`p99`（`9.74ms` vs `7.78ms`）略高**。 |
| `list_story_events`（遍历剧情 ZIP） | `65.37 / 80.46 / 87.71 ms` | **`40.47 / 44.22 / 60.57 ms`** | **显著胜出**：全分位大幅领先，`p50` 快约 **38%**，`p95` 快约 **45%**。 |
| `read_story`（专项单章读取） | `58.79 / 70.98 / 77.62 ms` | **`24.39 / 33.23 / 35.87 ms`** | **核心收益**：全分位快 **2.1×–2.4×**，`read_story` 专项峰值 RSS 从 `~270 MiB` 降至 `~248 MiB`；混合负载峰值 RSS 从 `~342 MiB` 降至 `~304 MiB`。 |

### 2.5 工具链兼容性核查：为什么不能直接跑 `bun test`？

在兼容性实测中，`bun run typecheck`、`bun run build` 与 `bun dist/server.js` 均直接通过，唯独 **`bun test tests` 无法通过现有单元测试套件**——原因是存量测试大量使用了 `node:test` 的特定 Runner 语义与生命周期行为，而当时 `Bun 1.3.14` 对 `node:test` 并非 100% 透明兼容。

## 3. 架构权衡与分阶段演进（2.0.2 → 2.2.0 → 3.0）

### 3.1 借鉴姊妹项目 `EndField-MCP` 的边界：取其构建/CD 拆分，不盲从其无状态传输与 Shebang

在制定迁移方案时，团队对照了同架构的 Bun-first 姊妹项目 `EndField-MCP`，明确划定了“可复用模式”与“不可盲目照搬的边界”：
1. **为什么保留 Node 启动入口（`prts-mcp-ts`）而不直接把默认 Shebang 改成 `#!/usr/bin/env bun`？**
   - 存量 `npx prts-mcp-ts` 用户与宿主机 `systemd` 部署默认环境只有 Node.js；若在小版本更新中直接把主入口 Shebang 改为 `bun`，会导致未安装 Bun 的宿主机立即启动失败。因此保留 `prts-mcp-ts` 的 Node 兼容性，通过新增 `prts-mcp-ts-bun` 提供显式 Bun 入口，而在运行时环境受控的 Docker 镜像中率先切为 Bun。
2. **为什么不把 Express + `StreamableHTTPServerTransport` 重写为 `Bun.serve`？**
   - `EndField-MCP` 采用每次 POST 新建实例的无状态 `Bun.serve`；而 PRTS-MCP 的 HTTP 传输依赖有状态会话 ID、24 小时空闲淘汰、过期会话 `initialize` 自动恢复（#142）以及连接级 `output_channel` 绑定。基准测试已证明直接用 Bun 运行现有编译产物即可拿到剧情 ZIP 读取 `2.4×` 提速，无需承担重写传输层的回归风险。
3. **为什么保留 Node 24 + `npm publish --provenance` 发布链路？**
   - npm 官方的 OIDC Trusted Publishing 与 Provenance 签名对 `npm` CLI 版本有严格要求；即便构建与冒烟阶段使用 Bun，在 CD 最后一步切回 Node 24 执行 `npm publish --provenance` 也能零风险保留完整的供应链签名保证。

| 版本阶段（日期为发布日期） | 实际工程动作 |
| --- | --- |
