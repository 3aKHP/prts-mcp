# 2.7 “上帝文件”解耦审计与 `DatasetAccess` 基石抽象

> **工程档案（2026-08 · v2.7.0 – v2.7.2）**：本文整理自 2.7 模块耦合度与双实现 Parity 审计底稿及 9-PR 重构执行记录（`#161`–`#171`），记录项目如何在 2.7 阶段通过抽取 `DatasetAccess` 基石抽象、将 `sync/` 独立分层以及系统性消除双端漂移，为后续 3.0 Rust 架构奠定清晰的模块边界。现行 3.x Rust 架构分层见 [`docs/dev/STYLE.md`](../dev/STYLE.md)。

---

## 1. 审计背景：为什么文件越来越长、双端漂移越来越频繁？

到 2.6.x 结束时，Python 与 TypeScript 两套代码库中出现了多个 500–1200 行的庞大模块（如 `sync.py` 1088 行 / `sync.ts` 1200 行、`enemy` 669/710 行）。更棘手的是，代码审阅中频繁发现双实现在边界输入、报错措辞、排序与同步超时上出现细微不一致（Parity Drift）。

2026-08-13，我们对全仓 **15 个核心业务单元**开展了以**“职责耦合度”**（而非单纯行数，`> 300` 行仅作为预警线）为标尺的系统性审计，辅以分层、Parity 与重复代码三项跨切面扫描，定位了三个深层根因：

### 根因一：缺失统一的 `DatasetAccess` 抽象（6 件套脚手架克隆）

在 `operator`、`enemy`、`stage`、`stage_enemy`、`item` 五个游戏数据域模块中，每个文件开头都原样复制粘贴了同一套 **6 件套样板代码**：
1. 获取运行时配置 `_get_config()`；
2. 从 `effective_excel_path` / `effective_levels_path` 构造 `_store()`；
3. 生成缺失数据提示文案 `_missing_X_data_message()`；
4. 挂接感知代际切换的缓存（Python 为 `@activation_aware_cache`，TypeScript 则是每个模块手写 `let` 变量 + `CacheMetrics` + `checkActivationChange()`，共 23 个 loader、约 200 行样板）；
5. 编写 `clear_X_caches()` 并向全局注册 `register_activation_listener()`；
6. 导出 `cache_stats()` 供 `/debug/cache` 读取。

因为缺少统一的 `DatasetAccess` 契约，不仅每个文件被迫把“缓存脚手架 + JSON 加载 + 结构构建 + Markdown 渲染”塞在一起，更导致 **`stage_enemy` 模块为了读取敌人与关卡表干脆自己重写了一套加载器**——造成同一份 `stage_table.json`、`enemy_handbook_table.json`、`enemy_database.json` 在内存中存在两份独立缓存，占用双倍内存且失效不同步。

### 根因二：`data/sync` 的分层断层与 5 个隐式“上帝类”

跨切面分层扫描显示，`api/`、`utils/`、`stores/`、`config` 均严格遵守分层约束，全仓唯一的分层断层集中在 `data/sync`（及其兄弟 `data/images_sync`）：
- 当时的 `STYLE.md` 一方面明文禁止 `data/` 发起 HTTP 请求或绕过 `stores` 直接操作文件系统，另一方面却在目录归属表中把 `sync` 列为 `data/` 居民，造成**规范条文与目录结构自相矛盾**；
- Python 的 `images_sync.py` 还跨模块导入了 `sync.py` 中 8 个以单下划线开头的“私有”符号（如 `_archive_activation_lock`、`_get_cascading`），并把镜像级联循环在 `_download_large` 中重造了一遍；
- `sync` 内部通过散落的自由函数和路径参数，隐式构成了 **5 个未封装的“状态 + 更新 + 查询”三要素（隐式上帝类）**：跨进程激活锁、Release 代际目录树、GameData 成对激活指针、立绘代际目录树（在 `images_sync` 中重复实现），以及 TS 侧的代理 Agent 单例；此外 `config` 内也藏着第 6 个隐式状态机（激活协调子系统）。

## 2. 两项核心架构裁决（D1 与 D2）

在动手拆分前，团队先锁定了两项全局裁决：

### 2.1 决策 D1：为什么必须“物理迁出 `sync/` + 修订 `STYLE.md`”，而非仅改规则？

针对 `data/sync` 的分层断层，当时比较了两种方案：
- **备选方案（仅修订文档规则）**：保持 `data/sync` 原地不动，只在 `STYLE.md` 中为 `data/sync` 增加一条允许发 HTTP 和直接读写磁盘的例外条款。
- **最终裁决（物理迁出至顶层 `sync/` 层 + 修订分层图）**：
  1. 若只改规则不移位，1200 行的同步状态机仍与纯粹的领域读取器混居在 `data/` 下，新贡献者难以一眼分清哪些模块受 `stores` 只读契约约束、哪些模块负责有副作用的网络与文件系统事务；
  2. 若只移位不立规，则只是把违规代码换个目录存放；
  3. 因此正式增设顶层 `sync/` 层，在 `STYLE.md` 中明确定义**“数据同步 HTTP 归 `sync/` 层，PRTS Wiki HTTP 归 `api/` 层，领域读取层 `data/` 严禁发起 HTTP”**，依赖方向设为 `sync → stores, utils, config`（过渡期允许 `data/sync` 作为纯 re-export barrel 转发 `sync/`）。

### 2.2 决策 D2：Parity 加固的“下限 vs. 上限”边界与遗留账本

跨切面审计發現了大量双端细节差异。为避免重构演变为无休止的逐字对齐，团队将 Parity 加固划分为**必做下限（纳入 2.7.0 `P4.A`/`P4.B` 独立修复 PR）**与**延后上限（登记入账本，按需在后续版本处理）**：

| 类别 | 具体项目 | 处理结果与落地位置 |
| --- | --- | --- |
| **D2 下限（2.7.0 立即修复）** | **GameData 列表分页边界缺失**：TS 声明了 Zod `limit .min(1).max(200)`、`offset .min(0)`，而 Python 缺少 `Field(ge=, le=)`（Story 工具两端本就齐全）。 | `P4.A`（`#161` → `948013b`）补齐 Python `Field` 边界，并扩展 `test_tool_surface.py` 校验参数数值上下界与正则标志位（堵住原先仅查参数名的盲区）。 |
| **D2 下限（2.7.0 立即修复）** | **TS 搜索正则缺少 `/u` 标志**：TS `new RegExp(pattern, "i")` 缺少 `/u`，处理非 BMP 字符（如扩展汉字、Emoji）时与默认 Unicode 的 Python `re` 分歧。 | `P4.A`（`#161`）统一改为 `"iu"` 编译（注：JS `\w` 即便带 `/u` 仍仅匹配 ASCII，而 Python `\w` 匹配中文字符，此语言级基础语义差异记录在案）。 |

| **D2 下限（2.7.0 立即修复）** | **`GITHUB_MIRRORS` 归一化、大图超时与锁异常类型**：TS 只去单个尾斜杠、Python 不去首尾空白且 `///` 产出坏候选；大图下载 Python 仅 300s 单次读超时而 TS 为 1800s 总期限；锁超时 TS 抛普通 `Error` 而 Python 抛 `TimeoutError`。 | `P4.B`（`#166` → `ee44b5e`）统一镜像 `trim + strip all '/'`、将 Python `_download_large` 对齐为每镜像候选 30 分钟 `time.monotonic()` 总期限，并导出具名 `ActivationLockTimeoutError`。 |
| **D2 上限（2.7.0 后续及账本）** | **错误提示引号与排序 Tie-break**：Python `repr` 单引号 vs. TS 双引号；TS `localeCompare` vs. Python 码点序。 | 剧情文本与未找到消息引号在 `2.7.0` 发布前对齐；全局码点序排序（`codePointCompare`）随后在 `2.7.2` 收口。 |
| **D2 登记保留的已知差异** | ① 敌人 blackboard 整数格式（PY `30` vs. TS `30.0`）与紧凑属性法术抗性渲染（PY `10.0` vs. TS `10`）；② TS `activeGenerationSync` 词法路径检查 vs. PY `Path.resolve()`（下游 `doGet` 已有 `realpath` 兜底）；③ 代际清理对悬空符号链接的处理（PY `stat` 报错跳过 vs. TS `lstat` 删除）。 | 在重构 CR 中用单元测试注释显式固定（pin）现状，不在重构 PR 中静默篡改行为，直至 3.0 统一以 TS/v2.8.1 为单一基线。 |

## 3. `DatasetAccess` 基石契约：重构前后对比

在 `P1.B`（`#167` → `276ee31`）落地的 `data/dataset_access.py` ↔ `data/datasetAccess.ts` 中，团队采用**“工厂函数 + 具名注册表”**统一收敛了配置读取、`Store` 构造、4 种缓存错误处理模式（`throw` / 三态失败缓存 / 负缓存 / 缺数据视为空字典）、激活失效监听与 `/debug/cache` 统计投影。

以道具模块（`item`）为例，重构前后的调用关系示意如下（省略部分加载器声明）：

```text
【重构前：每个数据域文件手写 6 件套（约 40–60 行样板）】
item.ts ──▶ import { loadConfig, checkActivationChange, registerActivationListener } from "../config.js"
        ──▶ import { DirectoryStore } from "./stores.js"
        ──▶ import { CacheMetrics } from "./cacheMetrics.js"
        ──▶ 手写 let _itemTableCache = null; const _itemMetrics = new CacheMetrics();
        ──▶ 手写 getStore() / missingItemDataMessage() / clearItemCaches() / getItemCacheStats()
        ──▶ registerActivationListener(clearItemCaches)

【重构后：声明式接入 DatasetAccess 注册表】
item.ts ──▶ const itemAccess = defineDataset({
              name: "item", loaders: { items: { load: loadItemsImpl }, ... },
              store: excelStore, missingMessage: excelMissingMessage("物品")
            });
        ──▶ const loadItems = itemAccess.loader("items");
        ──▶ export function clearItemCaches() { itemAccess.clear(); }
        ──▶ registerActivationListener(clearItemCaches)
        ──▶ /debug/cache 与 startupSync 直接从全局数据集注册表按固定键序自动汇总，无需手抄模块清单
```

这一改动还顺带修复了三处隐藏已久的可观测性问题：
1. `stage_enemy` 废弃了私有的重复加载器，改为直接调用 `enemy` 与 `stage` 导出的共享访问器，自身数据集仅保留 `enemy_appearance_index`，使 `/debug/cache` 消除了 4 个重复缓存键，并避免相同表在不同模块中重复加载与缓存；
2. TypeScript 的 `operator` 缓存计数原先统计的是顶层包装键（恒为 `1`），迁移后对齐 Python 统计内层 `handbookDict` / `charWords` 词条数；
3. 双轨 Code Review 揭示出模块注册表的插入顺序取决于传递性首次 `import` 顺序（Python 与 TS 不同），因此 `/debug/cache` 聚合改为**按显式固定模块键序投影**，并支持按域名覆盖重注册以兼容 TS 测试中的 `?cacheBust=` 动态重导入。

### 5.1 “纯结构移动”与“行为修复”严格分流的执行拓扑

```text
                   └──▶ P2.B.1 (#164, 0aae162: 迁出 release_activation / release)

```

### 5.2 关键教训：为什么 `re-export` 保不住迁出函数内部的测试 `monkeypatch`？

在执行 `P2.A`（`#163`）将 `check_latest_release`、`_list_releases` 与 `_get_cascading` 从 `prts_mcp.data.sync` 迁往 `prts_mcp.sync.release_discovery` 与 `prts_mcp.sync.transport` 时，团队遇到了一次极具代表性的测试失效：

- **预想假设**：只要在原模块 `prts_mcp/data/sync.py` 中保留 `from prts_mcp.sync.transport import get_cascading as _get_cascading` 重新导出，现有测试里写的 `monkeypatch.setattr("prts_mcp.data.sync._get_cascading", mock_fn)` 就应该继续生效。
- **实际暴雷**：`pytest` 运行 `test_sync_release.py` 时，4 个测试直接穿透了 mock、尝试发起真实网络请求并报错。
- **根因剖析**：Python（及 ES Module 内部直接调用）的函数在执行内部调用时，是在**定义该函数自身的模块全局命名空间（`__globals__`）**中解析被调函数名的。当 `_list_releases` 被迁入 `prts_mcp/sync/release_discovery.py` 后，它内部调用的 `get_cascading` 解析的是 `release_discovery`（或 `transport`）模块上的绑定；此时再去 patch 旧桶模块 `prts_mcp.data.sync._get_cascading`，只能替换掉外部通过 `data.sync` 直接访问的别名，对已迁出函数内部的调用链完全无效。
- **后续准则**：这一发现立即被写入 `P2.B` 与 `P3` 的执行守则——凡是迁移“内部调用了被测试 patch 符号”的函数，必须同步检索全仓测试中的 `patch` / `monkeypatch` 路径，将其重定向到实际发起调用的新子模块（或改为显式依赖注入），并在双轨 Code Review 中将“迁出函数内部符号解析”列为必查项。
