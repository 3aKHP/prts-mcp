# 1.0 架构定型与 1.5 运行时非功能性加固

> **工程档案（2026-05 · v1.0.0 – v1.6.0）**：本文整理自 1.0 架构规划、1.0 基线审计、1.0 Beta 硬化清单与 1.5 运行时非功能性审计报告，记录项目从 0.x 双端原型演进为 1.x 稳定数据层与常驻运行时架构的决策脉络。现行 3.x Rust 架构规范请参阅 [`docs/dev/STYLE.md`](../dev/STYLE.md)。

---

## 1. 背景：0.x 原型期的存储与代码割裂

在 0.x 过渡阶段（`python/v0.4.2`、`ts/v0.3.3`），PRTS-MCP 包含 Python（主攻 `stdio`）与 TypeScript（主攻 Streamable HTTP）两套并行实现，底层消费三类异构数据源：

| 数据集 | 上游来源与 Release 资产 | 0.x 运行时落地形态 | 直接读取方式 |
| --- | --- | --- | --- |
| **游戏数据表（`gamedata.excel`）** | `3aKHP/ArknightsGameData`（`zh_CN-excel.zip`） | 下载后解压为本地目录树 | `Path.read_text()` / `readFileSync()` 直接读散落 JSON |
| **剧情数据（`story.zh_CN`）** | `3aKHP/ArknightsStoryJson`（`zh_CN.zip`） | 保留 `.zip` 归档不解压 | 业务函数内直接打开 `zipfile.ZipFile` / `AdmZip` |
| **PRTS Wiki** | PRTS MediaWiki API | 无本地落盘 | 在线实时 HTTP 请求 |

2026-05-03 的 1.0 基线审计梳理出三个制约后续扩展的结构性问题：

1. **业务解析与物理存储介质硬耦合**：干员模块默认数据必定是解压目录，剧情模块则在工具函数内直接操作 ZIP 条目；一旦调整存储形态（例如评估游戏表是否直接读 ZIP），所有上层工具都要跟着改动。
2. **双实现同步与回退路径分散**：Python 与 TypeScript 各自在 `config`、`sync` 和启动脚本中维护了一套路径推导与回退顺序，缺少统一的抽象层来表达“用户自定义路径 → 运行时同步卷/用户目录 → 随包只读备用数据”的优先级。
3. **新数据域扩展成本高**：每增加一个读取游戏表的新工具，都需要重复编写必需文件完整性检查、缺数据降级提示与缓存清理钩子。

## 2. 1.0 四层数据访问架构与设计取舍

为了在不改变现有 9 个公共 MCP 工具名与必填参数的前提下完成内部收敛，1.0 架构确立了四项核心原则：**保持外部行为稳定、先统一读取概念而非物理存储、让新工具开发由数据规格驱动、保留各发行渠道的体积定位**。

```text
1. Dataset Source  ← 声明数据集规格（dataset id、上游仓库、Release 资产名、必需内部路径、回退策略）
2. Local Storage   ← 屏蔽底层物理介质（DirectoryStore / ZipStore / FallbackStore）
3. JSON Reader     ← 提供跨语言一致的最小读取接口：exists / read_text / read_json（及可选 list / describe）
4. Domain Parser   ← 只关心明日方舟业务数据结构（OperatorRepository / StoryRepository 等）
```

### 2.1 统一“读取概念”而非强制统一“物理存储”

1.0 的关键取舍是**不要求所有数据集在磁盘上采用同一种物理形态**。游戏数据表（`character_table.json`、`handbook_info_table.json`、`charword_table.json`、`story_review_table.json`）继续解压为目录树以兼容 `GAMEDATA_PATH` 本地仓库挂载；剧情数据（`zh_CN.zip`，含 `story_review_table.json` 与数千个 `zh_CN/gamedata/story/{story_key}.json` 章节条目）继续保持单文件 ZIP 归档以避免向磁盘释放海量小文件。

通过引入三类 `Store` 实现，物理形态差异被彻底隔离在存储层内部：

- **`DirectoryStore`**：以本地目录为根读取文本与 JSON；
- **`ZipStore`**：直接按归档内部相对路径读取 ZIP 条目；
- **`FallbackStore`**：组合“主存储（用户自定义路径或自动同步目录）”与“内置备用存储（bundled store）”，主存储完整时优先使用，缺失时无缝回退至随包只读数据。

### 2.2 为什么坚持“最小接口约束”并先迁移存量工具？

针对“过早过度抽象”的风险，1.0 对 `JSON Reader` 施加了严格的设计约束：

- **必选核心接口仅 3 个**：`exists(path) -> bool`、`read_text(path) -> str`、`read_json(path) -> object`（辅以诊断用的 `describe()`）；
- **`list(prefix)` 列为 1.0 可选能力**：存量干员工具读取固定表名，剧情工具通过 `story_review_table.json` 索引直接定位 `{story_key}.json`，均无需目录枚举；
- **先迁移存量工具，再扩展新能力**：Phase 1–3 先将现有干员与剧情解析器平滑迁移到新接口上，验证抽象足够精简有效，同时将计划中探讨的“剧情摘要工具（`get_story_summary`）”显式推迟到 1.0 数据层稳定之后，避免架构迁移与新功能开发交织。

### 2.3 双实现同构（Parity）的明确边界

1.0 明确界定了 Python 与 TypeScript 双实现同构的范围：**共享行为语义与跨语言测试夹具，但不强制内部类名或语言惯用法逐字相同**。

- 两端围绕同一份手写最小测试夹具（包含 1 名干员的基础信息/档案/语音、1 个含两章剧情的活动，以及缺失数据用例）分别验证 `DirectoryStore`、`ZipStore` 与 `FallbackStore`；
- 干员与剧情工具的成功输出文本、缺失数据提示、ZIP 解压路径安全检查（拒绝 `..` 路径穿越）在两端保持一致；
- 发布流程要求 `python/v1.0.0-alpha.1` 与 `ts/v1.0.0-alpha.1`（及后续正式版 [`python/v1.0.0`](https://github.com/3aKHP/PRTS-MCP/tree/python/v1.0.0)、[`ts/v1.0.0`](https://github.com/3aKHP/PRTS-MCP/tree/ts/v1.0.0)）从同一提交基线打标发布，防止双端在演进中悄然漂移。

### 2.4 发行形态取舍与三级路径优先级

基线审计与 Phase 4 确立了三种发行渠道的差异化打包策略（由 CI 中的 `python/scripts/check_package_data.py` 强制校验）：

| 发行渠道 | 随包备用数据策略 | 原因与运行回退关系 |
| --- | --- | --- |
| **Docker 镜像** | 内置 `/app/data/gamedata` 与 `/app/data/storyjson/zh_CN.zip` | 容器默认将 `/data/gamedata` 与 `/data/storyjson` 作为可写同步卷；卷内尚无完整数据时立即回退至 `/app/data` 只读备用数据，保证断网或首启期间立即可用。 |
| **npm 包（`prts-mcp-ts`）** | CD 发布前预热 `ts/data/gamedata` 与 `ts/data/storyjson/zh_CN.zip` | 保证 `npx` 用户开箱即用；运行时同步写入用户数据目录（`~/.local/share/prts-mcp/` 或 `%LOCALAPPDATA%\prts-mcp`），优先于 `<package_root>/data/` 下的随包备用数据。 |
| **PyPI 包（`prts-mcp`）** | **不打包**大型备用数据（仅包含 `src/prts_mcp` 代码） | 保持 Python Wheel 轻量；首次启动时通过后台守护线程异步拉取 Release 资产，或由用户通过 `GAMEDATA_PATH` / `STORYJSON_PATH` 指定本地数据（显式设置路径即自动禁用对应数据集的后台同步）。 |

## 3. 原始规划中的开放问题与实际落地对照

1.0 架构规划中记录的若干候选设想，在后续版本中的实际走向如下：

- **游戏数据表是否改为直接从 `zh_CN-excel.zip` 读取？** 最终保留了解压为目录树的默认方式（由 `DirectoryStore` 读取），既保持了与外部 `ArknightsGameData` 目录结构的直接兼容，又在后续 2.4 引入成对代际目录激活时实现了零拷贝原子切换。
- **缓存元数据放在 `archives/` 还是集中目录？** 落地为跟随各数据集根目录存放（如 `archives/release_meta.json`、`archives/extract_meta.json`），便于单卷挂载与数据集独立迁移。
- **剧情摘要工具（Optional Story Summary Track）如何推进？** `1.0.0` 正式版按计划未纳入摘要工具；`get_story_summary(story_key)` 随后在 1.1–1.2 阶段基于 `storyinfo.json` 与长摘要数据源落地；而规划中列为延后项的 `get_stage_story_summary(stage_id)` 因关卡与剧情已可通过 `list_stories` / `get_stage_info` 清晰查得，最终未作为独立工具引入。

## 4. 1.4.1 前置治理与 1.5 运行时非功能性审计

随着 1.3–1.5 陆续引入 PRTS 页面结构工具、模板解析（`get_prts_template`）、敌方图鉴（`enemy`）与关卡数据域（`stage`），工具数扩展至 24 个，服务在生产环境中作为长期常驻进程运行。

在 2026-05-19 的 `1.4.1` 中，团队率先修复了第一批性能与内存瓶颈：
- 为 `ZipStore` 增加实例内的 `ZipFile` / `AdmZip` 缓存，并将 Python `exists()` 从 $O(n)$ 的 `namelist()` 改为 $O(1)$ 的 `getinfo()`，消除了无过滤 `search_stories` 单次调用触发约 3000 次冗余 ZIP 打开导致超过客户端 120 秒超时的问题；
- 在 Python 侧引入进程级共享 `httpx.AsyncClient` 替代 7 处按调用新建客户端，在 TypeScript 侧引入 `SESSION_IDLE_TIMEOUT_MS`（1.4.1 默认 30 分钟，1.4.2 延至 24 小时并规范化过期会话返回 HTTP 404 / `-32002`）解决断开会话的内存累積。

在此基础上，2026-05-28 开展了 **1.5 运行时非功能性专项审计**（相关修复随同日发布的 [`python/v1.6.0`](https://github.com/3aKHP/PRTS-MCP/tree/python/v1.6.0) 与 [`ts/v1.6.0`](https://github.com/3aKHP/PRTS-MCP/tree/ts/v1.6.0) 落地），全面排查了存储生命周期、回退校验、缓存失效与定时器残留。

### 4.1 审计确认并修复的三项缺陷（`Findings Fixed`）

1. **Python `ZipStore` 句柄确定性关闭**：
   - **问题**：1.4.1 让 `ZipStore` 在实例内缓存了打开的 `zipfile.ZipFile`，但剧情模块按 ZIP 路径工作的辅助函数在每次调用时都会创建临时 `ZipStore` 实例，未显式关闭底层句柄。虽然 CPython 引用计数通常会在函数返回后回收，但高频剧情读取与全文搜索不应依赖垃圾回收器（GC）来释放文件描述符。
   - **修复**：为 `ZipStore` 实现显式 `close()` 与上下文管理器（`with ZipStore(...) as store`），令 `DirectoryStore.close()` 为空操作、`FallbackStore.close()` 向下传递至子存储，并将所有 Python 剧情辅助函数改为通过 `with` 块在每次调用结束时确定性释放 ZIP 句柄。
2. **TypeScript 缓存 Release ZIP 回退完整性校验对齐**：
   - **问题**：Python 的 `sync_release()` 在网络异常回退到本地已缓存的 `zh_CN.zip` 前会执行完整性校验；而 TypeScript 的 `syncRelease()` 仅检查文件是否存在。若本地残留了损坏或下载中断的 `zh_CN.zip`，TypeScript 会将其误报为健康的 `offline_fallback`，直到后续工具调用读取归档时才报错失败。
   - **修复**：令 TypeScript `syncRelease()` 对已存在的缓存 ZIP 同样执行数据集校验器（`validateZip`）；当校验不通过或校验器抛出异常时判定缓存不可用，在无网络时诚实返回 `no_data`，与 Python 行为严格对齐。
3. **TypeScript 会话空闲定时器 `.unref()` 生命周期**：
   - **问题**：启动同步的重试定时器已调用 `.unref()`，但 HTTP 会话池为每个活跃会话创建的空闲淘汰定时器在挂起期间未调用 `.unref()`，导致进程在无活跃请求、等待优雅退出时仍被未到期的会话定时器阻塞事件循环。
   - **修复**：在调度会话空闲定时器后立即调用 `.unref()`。

*(注：同日发布的 `1.6.0` 在引入 `zh_CN-levels.zip` 时，还一并补充了压缩包解压前后的双阶段必需条目校验，并将 `get_enemy_appearances` 改为按目标敌人扫描而非首次调用时永久缓存全量敌人出场索引。)*

### 4.2 审计评估后确认可接受的现有机制（`Findings Confirmed Acceptable`）

审计并非对所有模块一刀切重写，以下机制经核查被判定为设计合理、无需在当次改动：

- **表缓存与同步后失效机制**：Python 的 `lru_cache(maxsize=1)` 与 TypeScript 的模块级单例表缓存均为有界缓存，且在启动同步写入更新后的 GameData 时，两端均已正确清理 `operator`、`enemy` 与 `stage` 缓存。
- **有界重试循环**：启动同步在遇到 `offline_fallback` 或 `no_data` 时最多重试 3 次（30s、120s、600s）；Python 使用守护线程定时器，TypeScript 使用已 `.unref()` 的定时器，不存在无限重试泄漏。
- **同步资产整包内存缓冲**：当时 Release 压缩包体积有限且采用“写临时文件 + 原子重命名”落盘，整包缓冲不会造成持续内存泄漏（直到 2.5 引入 GB 级立绘分片时才专门引入流式下载 `downloadLarge`）。
- **Python 共享 `httpx.AsyncClient` 关闭钩子**：由于当时本地测试环境的 FastMCP 尚未暴露稳定的进程停机生命周期钩子，审计决定保留进程级连接池复用，不强行注入推测性的事件循环关闭逻辑。

### 4.3 确定性关闭 vs. 重复实例化开销的权衡（`Residual Risks`）

在修复 Python `ZipStore` 句柄泄漏时，团队明确记录了一项性能与可靠性的折中：让剧情包装函数在每次调用结束时 `close()` 临时 `ZipStore`，意味着**每次工具调用仍会重新打开一次 `zh_CN.zip` 并解析其 Central Directory**（1.4.1 解决的是“单次调用内部 3000 次重复打开”，而跨调用仍保持一调一开一关）。

审计将跨调用的重复解析开销列为后续优化方向：若性能分析表明值得优化，可以考虑在仓库层复用剧情存储缓存。当次修复先保证句柄确定性关闭，未引入跨调用的常驻 `ZipStore` 缓存。
