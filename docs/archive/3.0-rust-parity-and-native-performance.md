# 3.0 Rust 行为复刻、QuickJS C 正则剥离与原生性能报告

> **工程档案（2026-10 · v3.0.0 内核攻关与 P1/P9 基准报告）**：本文整理自 3.0 Rust 重写调研（[`docs/dev/rust-rewrite/docs/10-research.md`](https://github.com/3aKHP/PRTS-MCP/blob/v3.0.0-alpha.3/docs/dev/rust-rewrite/docs/10-research.md)）、[P1 协议与语言兼容报告](https://github.com/3aKHP/PRTS-MCP/blob/v3.0.0-alpha.3/docs/dev/rust-rewrite/reports/P1.md)与 [P9 原生性能专项报告](https://github.com/3aKHP/PRTS-MCP/blob/v3.0.0-alpha.3/docs/dev/rust-rewrite/reports/P9-native-performance.md)，记录团队如何评估协议 SDK 与正则候选方案，以及如何从“内嵌完整 QuickJS VM 的起点 Rust”演进到“独立静态 `libregexp.c` + 字节码前缀加速 + 四线程单飞索引”的最终形态。

## 1. 复刻 TS/v2.8.1（Oracle）的四道技术鸿沟

将 `TS/v2.8.1`（固定基准 Commit `e0ba36096cdd46640166b0a5db02902fa9a6a24c`，`Bun 1.3.14`）的 59 个业务源文件（12,650 行）迁移至原生 Rust，并要求通过全部 **384 项离线 MCP 契约差分用例**与 **325 项 Wiki 清洗对照用例**，核心难点集中在以下四个跨语言与协议边界：

1. **MCP 双时代传输指纹（`legacy` vs. `2026-07-28 modern`）**：不仅要支持 `stdio` 与 Streamable HTTP，还要在 HTTP 状态码、SSE 事件帧格式、未知会话 `-32002` 响应、携带过时会话 ID 的 `initialize` 自动恢复，以及 `modern` 时代无状态信封校验（`-32020` / `-32022`）上与原 Express + TS SDK v2 实现保持 wire 级兼容。
2. **ECMAScript 正则语法与“无限长后顾断言”**：`search` 与 `search_stories` 向用户暴露了完整的 JavaScript `/iu` 正则语法，包括正向/反向先行断言（Lookahead）、命名/数字反向引用以及**不定长后顾断言（Variable-Length Lookbehind，如 `(?<=a+)b`）**。
3. **JavaScript UTF-16 码元序与数值格式化**：列表排序（`compareIds`）与切片基于 UTF-16 码元（Code Unit）而非 UTF-8 字节或 Unicode 码点；面板线性插值与黑板数值渲染需严格遵循 JS `Number::toString()` 与整数判定（如 `1.0` 视为整数 `1`）规则。
4. **42.4 万行剧情归档的冷索引与全表扫描性能**：生产剧情包 `zh_CN.zip` 含 **2,285 章、424,281 条对话/旁白记录**，稍有不慎就会因跨语言正则调用或锁竞争导致冷启动与全表扫描比 `Bun 1.3.14` 更慢。

## 2. 协议层选型实证：为什么从 `rmcp 3.5.1` 转向 `src/protocol` 薄适配？

在 P1 阶段，团队首先按 `10-research` 计划编写了独立探针 [`examples/rmcp_probe.rs`](../../examples/rmcp_probe.rs)，以与 TS Oracle 完全相同的服务身份启动官方 Rust SDK `rmcp 3.5.1` 的 `StreamableHttpService`，并与冻结的 `contracts/wire/` 基准进行了逐项比对。

### 2.1 `rmcp 3.5.1` 探针实测暴露的 6 处 Wire 差异

| 协议交互场景 | TS/v2.8.1 Oracle 基准行为 | `rmcp 3.5.1` 默认传输行为 |
| --- | --- | --- |
| **1. `legacy` POST 响应帧** | 直接返回 `event: message\ndata: ...`，无 priming 事件 | 先发送 priming 事件（`data:\nid: 0\nretry: 3000`），且消息帧无 `event: message` 名称、附带 `id: 1/0` 及额外缓存响应头 |
| **2. 未知/过期会话 ID** | 返回 HTTP `404` + JSON-RPC `-32002` 及项目定制可操作提示 | 返回 HTTP `404` 纯文本 `Not Found: Session not found` |
| **3. `server/discover` 发现** | 返回 `application/json`，仅声明 `supportedVersions: ["2026-07-28"]` | 返回 SSE 流 + priming，并列出 5 个协议版本 |
| **4. `modern` 时代响应格式** | 恒为 `application/json`，成功结果附带 `resultType` / `ttlMs` / `cacheScope` / `_meta.serverInfo` | 仍封装为 `text/event-stream`（SSE） |
| **5. `modern` 损坏信封报错** | 返回项目结构化错误码与 `data.envelope.missing` 等精确字段 | 错误消息与 `data` 字段结构不同 |
| **6. 携带过时会话 ID 的 `initialize`** | 自动剥离失效的 `mcp-session-id` 并作为全新握手恢复（#142 放宽策略） | 无此自动恢复语义，直接按未知会话拒绝 |

### 2.2 薄协议适配层的边界与获批协议差异（`D-001` / `D-005` / `D-006`）

实测证明，`rmcp 3.5.1` 的高层传输封装无法仅靠配置项复现 PRTS-MCP 既有的双时代 wire 指纹。因此，团队触发了风险表中预置的**“薄协议适配（Thin Protocol Adaptation）”**路径：
- **什么叫“薄适配”而非“重造庞大的私有协议栈”？** PRTS-MCP 仅使用了 MCP 协议中极小的一个子集（`initialize`、`notifications/initialized`、`tools/list`、`tools/call`、`server/discover` 及四类传输错误），从未暴露 `resources`、`prompts`、`sampling`、`roots` 或 OAuth 鉴权。因此在 [`src/protocol/`](../../src/protocol/) 中直接基于 `axum` 与 `serde_json` 编写精确对齐 wire 基准的薄分发器，代码精简且完全可控；同时将 `rmcp` 保留在 `dev-dependencies` 与 `examples/rmcp_probe.rs` 中作为可随时复跑的选型证据。
- **P1 明确登记的协议层兼容差异**：除版本号归一化（`D-001`）外，维护者在 P1 正式批准了两项比 TS Oracle 更规范的输入边界差异——**`D-005-input-surrogate-rejection`**（Rust 在 HTTP 层拒绝含孤立 UTF-16 代理码元的畸形 JSON 并返回 HTTP 400 + JSON-RPC `-32700`，而配对代理码元如 `U+20BB7` 正常通过）与 **`D-006-unparseable-body-json-error`**（HTTP 请求体 JSON 语法损坏时返回标准 HTTP 400 + JSON-RPC `-32700`，替代原 Express 默认的 HTML 错误页）。

## 3. 正则引擎与剧情索引的四步演进链（从 P1 到 P9）

### 3.1 五种正则候选方案的实测与淘汰路径

为了在不缩减用户正则语法的前提下对齐 JS `RegExp("/.../iu")`，团队先后评估并实测了五种方案：

| 候选方案 | 评估阶段 | 实测表现与取舍结论 |
| --- | --- | --- |
| **1. Rust `regex` crate** | `10-research` | ❌ **淘汰**：为保证线性时间复杂度，设计上不支持环视断言（Lookahead / Lookbehind）与反向引用，无法运行存量高级查询。 |
| **2. `regress 0.12.0`** | `10-research` | ❌ **淘汰**：虽面向 ECMAScript 语法并支持回溯，但官方文档明确存在 Unicode 属性转义（`\p{...}`）支持缺口。 |
| **3. 原生 `PCRE2` 探针** | `P9` 实测 | ❌ **淘汰**：编写原生探针实测发现，PCRE2 拒绝编译 Bun/JS 合法支持的**无限长后顾断言**（如 `(?<=a+)b`），存在破坏用户既有查询契约的风险。 |
| **4. `rquickjs 0.14.0`（完整 QuickJS VM）** | `P1` – `P8`（“起点 Rust”） | ⚠️ **过渡方案（P9 移除）**：通过内嵌完整 QuickJS 虚拟机，在 P1–P8 实现了 49 项黄金正则语料 100% 通过；但每次匹配需跨越 VM 锁与上下文边界，导致 P8/P9 起点版本在全表扫描 42.4 万行时耗时高达 `360.35 ms`（比 TS/Bun 慢 16 倍）。 |
| **5. 独立剥离 QuickJS `libregexp.c` + 字节码前缀加速** | `P9`（最终生产方案） | ✅ **最终选定**：从同一固定 SHA-256 的 `rquickjs-sys 0.14.0` 源码包中仅抽出 7 个纯 C 正则与 Unicode 文件（存放在 [`vendor/quickjs-regexp/`](../../vendor/quickjs-regexp/README.md)），由 `cc` 编译为静态库，**彻底移除 `quickjs.c` 与整个 JS 虚拟机**。 |

### 3.2 从“起点 Rust”到“最终 Rust”的性能突围四步曲

在 P9 专项优化中，团队在不改变任何工具契约、不预建离线索引、不缓存单次查询结果的前提下，通过四项改造攻克了“起点 Rust”的性能瓶颈：

1. **剥离 JS VM + 线程内 UTF-16 Scratch 缓冲区复用（[`native/regexp.c`](../../native/regexp.c)、[`src/text/regex_compat.rs`](../../src/text/regex_compat.rs)）**：
   - 删除 `rquickjs` 依赖，通过极薄的 C FFI 直接调用 `lre_compile` 与 `lre_exec`；在每个工作线程内复用 UTF-16 转换缓冲区，消除 42.4 万次匹配中的重复堆分配与 VM 锁竞争（通过 `tools/check-native-binary.mjs` 验证最终二进制零 JS VM 符号）。
2. **编译期字节码字面量前缀提取（Literal Prefix Acceleration）**：
   - 正则编译完成后，直接静态扫描 `libregexp` 输出的线性字节码指令流，提取模式开头的**必需字面量前缀**（一旦遇到分支跳转、环视断言或非确定性量词立即停止）；
   - 在扫描剧情记录时，若目标行不包含该必需前缀，直接在 Rust 层快速排除而无需进入 C 正则状态机；纯字面量模式在前缀命中后直接确认；带先行/后顾断言或复杂量词的模式则在前缀筛出候选行后交由同一个 `libregexp` 内核精确判定；遇到特殊 Unicode 大小写折叠字符（如 `ſ`、`K`、`ẞ`）时自动保留原生 C 路径，并对整张内置 Unicode 表进行了穷举验证。
3. **四线程并行章节解析 + 同代单飞锁（Single-Flight Index Lock）**：
   - 起点 Rust 在单线程内串行完成 ZIP 读取与 JSON 反序列化，导致冷索引耗时 `2,103.42 ms`；
   - 最终 Rust 将“ZIP 条目串行读取 + 路径/CRC 校验”与“耗时的章节 JSON 解析 + 指令提取”解耦，将章节解析分发至最多 **4 个工作线程**并行执行，最后按章节原始 `ordinal` 确定性归并；同时增加同代单飞索引锁，杜绝并发请求同时重复构建同一份索引。
4. **无标签文本零分配清洗（[`src/text/sanitizer.rs`](../../src/text/sanitizer.rs)）**：
   - 在读取章节与清洗 Wiki 文本时，直接借用已有字符串切片，对不含 HTML/富文本标签的普通台词跳过 `Vec<char>` 预分配，使 325 项冻结 TS 辅助函数对照用例 100% 零差异通过。

## 5. 功能等价、扩展正则语料（`D-007`）与内存安全验证的边界区分

在 P9 验收中，团队将**业务输出全等验证**、**扩展正则语料差分（`D-007`）**与 **C 代码内存安全消毒（Sanitizers）**严格区分为三项独立结论，互不混同：

1. **业务契约与全量剧情索引 100% 全等**：
   - 全量离线 MCP 差分套件 **`384 / 384` 全部通过**；Wiki 辅助函数对照 **`325 / 325` 全部一致**；
   - 全量剧情索引摘要（`examples/story_index_digest.rs`）对 **2,285 章 / 424,281 条记录**的元数据、台词类型、说话人、正文与记录序号计算出的 SHA-256 为 `96f0115147139a8a3b977727f779e0a5a26a8aed5516505be2664518e6c4363c`，与 TS Oracle **逐字节全等**；P9 基准中全部热查询的返回报文哈希也与 TS 100% 相等。
2. **扩展正则语料测试与 `D-007-native-regex-unicode-folding` 的精确定义**：
   - 在原始 **49 项**黄金正则语料中，最终 Rust 与 Bun（JavaScriptCore）**100% 一致**；
   - 在进一步构造的 **3,276 项**极端组合扩展语料中，**3,190 项**与 Bun 严格一致，其余 **86 项**全部落在同一机制的两个已知类别中（用旧 `rquickjs` 适配器重跑也得到完全相同的 86 项，证明并非剥离 C 组件或前缀加速引入的新回归）：
     - **类别 A（ASCII 范围跨域大小写折叠）**：在 `/iu` 标志下，QuickJS `libregexp` 对 `[a-zA-Z]` 或 `[s-s]` 应用 Unicode Simple Case Folding，因此会匹配折叠到 ASCII `s`/`k` 的拉丁长 s `ſ`（`U+017F`）与开尔文符号 `K`（`U+212A`），而 Bun 的 JSC 不折叠；
     - **类别 B（Unicode 属性转义的大小写折叠闭包）**：在 `/iu` 标志下，`\p{Lowercase_Letter}` 及其反向属性 `\P{Lowercase_Letter}` 在 QuickJS `libregexp` 中按忽略大小写扩展匹配（如 `\p{Lowercase_Letter}` 在 `/iu` 下匹配 `"ABC"`），而 Bun 保持大小写敏感的属性集合。
   - 维护者于 2026-10-13 将上述两类明确界定的差异批准登记为 **`D-007-native-regex-unicode-folding`**，并将全部 86 个最小复现用例与两端预期值锁定在 [`contracts/cases/native-regex-differences.json`](../../contracts/cases/native-regex-differences.json) 中逐项回归校验。**注意：`D-007` 仅豁免上述两类特定的 Unicode 大小写折叠差异，绝不代表豁免其他无关的正则差异，也不将有限语料通过夸大为全量 ECMAScript 语法的数学等价证明。**
3. **C 正则组件的 ASan / UBSan / LeakSanitizer 内存安全验证**：
   - 使用 Clang 的 `AddressSanitizer`、`UndefinedBehaviorSanitizer` 与 `LeakSanitizer` 编译 `vendor/quickjs-regexp/` 及 `native/regexp.c`，完整跑通全部 3,276 项扩展正则语料（`tools/check-native-regexp.mjs`），实现**零内存越界、零未定义行为、零内存泄漏**。这一结论证明的是原生 C 正则绑定层的内存与生命周期安全，与上一条的语法语义对照各司其职。
