# 2.0 工具面收敛（32 → 23）与双输出通道设计

> **工程档案（2026-07 · v2.0.0）**：本文整合自 2.0 工具面合并设计稿、输出通道设计稿、P1 后续修补及 TS 轨道交接记录，复盘 2.0 大版本在“128K 模型上下文预算控制”与“结构化输出通道”上的架构权衡与 SDK 底层实证。迁移操作说明见 [`docs/migration-1.x-to-2.0.md`](../migration-1.x-to-2.0.md)。

---

## 1. 背景：32 个工具带来的上下文膨胀与选择歧义

到 1.7.0 LTS 发布时，PRTS-MCP 的工具总数已从最初的十几个膨胀到 **32 个**。根本原因在于 1.x 形成了“每增加一个数据域就机械复制 `list_X` / `get_X` / `search_X` 三件套”的惯性。

对于 128K 上下文窗口的模型及主流客户端，工具过多带来了两个实质性痛点：
1. **Prompt Token 固定税**：MCP 协议当时尚无通用的按需延迟加载（Deferred Tool Loading）机制，每次会话的每个轮次都必须把全部 32 个工具的完整 JSON Schema 与描述塞入系统提示词；
2. **近义词干扰（Selection Accuracy 下降）**：当 `search_data`、`search_enemies`、`search_stages`、`search_items` 或 5 个 `prts_page` 相关工具并列时，LLM 需要在形态几乎相同的近义工具之间做选择，误选率明显上升。

因此，2.0 的目标不只是在当次版本减少工具数量，更是**确立“优先枚举扩展（`scope` / `action`）而非新增顶层工具”的演进原则，压平未来新数据域推高工具数的斜率**。

## 2. 工具面收敛判据与具体取舍（32 → 23）

在决定哪些工具应该合并、哪些必须保持独立时，团队确立了“质量风险可约 vs. 不可约”的唯一判据：

- **可约风险（适合合并）**：风险仅来自表层参数设计（如判别式带含糊默认值、参数命名不统一、多个工具实为同构近义词）。通过**必填无默认值的 `enum` 判别式 + 统一参数命名 + 工具描述工作流指引**即可消除误用风险。
- **不可约风险（禁止强行合并）**：风险来自输出内容本身的异质性（例如“大段叙事散文” vs. “精确数值面板” vs. “逐句对话台词”）。若强行用 `mode` 参数塞进同一个“全能工具”，只会迫使模型在截然不同的推理模式间混用同一个入口。

### 2.1 三组收敛方案汇总（净减 9 个工具）

| 收敛项 | 1.x 原工具（共 12 个） | 2.0 合并后（共 3 个） | 净变化与核心设计要点 |
| --- | --- | --- | --- |
| **跨域统一正则搜索** | `search_data`、`search_enemies`、`search_stages`、`search_items`、`list_search_scopes` | `search(scope, pattern, max_results?)` | **−4**：`scope` 为必填无默认值枚举（2.0 为 `operators \| enemies \| stages \| items`，2.7/2.8 扩展至 6 个域且零新增工具）；原 `list_search_scopes` 的目录说明直接内联进 `search` 描述；`search_stories` 因独有 `character`/`line_type`/`context_lines`/`event_id` 富过滤参数而保持独立。 |
| **PRTS 维基页面操作** | `read_prts_page`、`list_prts_sections`、`get_prts_categories`、`get_prts_links`、`get_prts_template` | `prts_page(page_title, action, ...)` | **−4**：采用**全 action 化**（必填枚举 `read \| sections \| categories \| links \| template`）；`search_prts` 因走 MediaWiki 实时关键词搜索而保持独立。 |
| **活动剧情目录与概览** | `list_stories`、`get_event_summary` | `list_stories(event_id, include_summaries?)` | **−1**：先让 `list_stories(include_summaries=true)` 吸收活动级 LLM 长摘要成为 `get_event_summary` 的严格超集，再删除后者；单章深摘要 `get_story_summary` 保持独立。 |

### 2.2 关键取舍一：`prts_page` 全 action 化与工具描述补偿

在合并 PRTS 维基页面工具时，曾对比过两种深度的方案：
- **保守方案**：仅合并低频的 `categories`、`links`、`template`，保留高频的 `read_prts_page` 与 `list_prts_sections` 独立；
- **全 action 化方案（最终选定）**：将全部 5 个针对已知页面标题的操作收归 `prts_page(page_title, action, ...)`，仅按需暴露条件参数（`read` 用 `section_index?`，`links` 用 `direction?` 与 `limit?`）。

选择全 action 化的明确代价是：**原先由两个工具名自然暗示的“先看目录（`list_prts_sections`）→ 再按编号读章节（`read_prts_page`）”高频工作流，在合并后变得不再直观**。为此，设计稿明确采用**工具描述补偿策略**：在 `prts_page` 的描述首段直接写明推荐调用链——“先用 `action="sections"` 看目录（每行 `[编号] L层级 标题`），再用 `action="read"` + `section_index` 读特定章节，避免整页过载”。

### 2.3 关键取舍二：为什么 `list_stories` 必须先补入活动长摘要才能替代 `get_event_summary`？

在审查 `list_stories(include_summaries=True)` 与 `get_event_summary` 时，代码核查证实两者在 1.x 中处于**“部分重叠、互不包含”**的状态：

| 输出要素 | 1.x `list_stories(include_summaries=true)` | 1.x `get_event_summary` |
| --- | :---: | :---: |
| 章节官方顺序与每章一句话梗概（来自 `storyinfo.json`） | ✅ | ✅（重复技术债） |
| 可直接传给 `read_story` 的每章 `story_key` 导航句柄 | ✅ | ❌ |
| 活动级 LLM 整体长摘要（来自可选的 `event_summaries.json`） | ❌ | ✅（独有能力） |

因此，`list_stories` 在 1.x 原状下**并非** `get_event_summary` 的天然替代品。2.0 的落地顺序是：先改造 `list_stories`，当 `include_summaries=true` 且数据包内存在 `event_summaries.json` 时，在章节列表顶部前置输出活动级长摘要，使其成为 `get_event_summary` 的严格超集（且额外附带每章 `story_key` 便于后续直读），随后才安全移除 `get_event_summary`。

### 2.4 关键取舍三：为什么 2.0 直接硬切、不保留旧工具名 Alias？

2.0 决定对被合并/重命名的工具采取**直接硬切（Hard Cutover），不注册任何 deprecated alias**，理由如下：
1. **保留 alias 会让上下文瘦身归零**：MCP 服务端一旦注册 alias 工具，客户端在 `tools/list` 中依然会收到全部 32 个工具的 Schema，128K 模型的固定 Token 税与近义工具选择干扰丝毫不会减少；
2. **已有 1.7 LTS 承接存量用户**：团队在开启 2.0 前已正式切出 `1.7.0` LTS 分支（承诺维护至 2027-07-02），不希望修改调用方的环境可继续锁定 1.7.x，而 2.0 作为语义化大版本理应一次性清理历史包袱。

同时，2.0 将分步执行拆为 5 个 PR：PR #1 先完成零风险的参数命名归一化（将 `get_operator_*` / `get_operator_memoirs` 的 `operator_name` 统一改为与其他域一致的 `name`，固化分页 `limit`+`offset` 与正则 `pattern`+`max_results` 约定）并在 `STYLE.md` 中确立工具描述规范（Spec）；PR #2–#4 依次完成三项合并；PR #5 在工具面冻结后对全部 23 个工具执行描述瘦身（Sweep），避免中途反复重写被删工具的文案。

## 3. 双输出通道设计：从“默认翻转 JSON”到正交 `output_channel`

### 3.1 为什么否决早期路线图中的 `output_format=json` 默认翻转？

1.x 路线图曾设想在每个工具上增加 per-call 参数 `output_format = "markdown" | "json"` 并在 2.0 将默认值翻转为 `json`。2026-07-02 的设计评估否决了这一方案：

1. **Token 估算与省预算主题相悖**：按设计期估算，将包含大量中文叙事与列表的内容编码为带转义符与重复键名的 JSON 字符串，相比等价紧凑 Markdown 约多消耗 **15%–30%+ 的 Token**（注：此数值为设计阶段针对叙事与列表载荷结构的估算口径，非固定基准测试值），若默认翻转等于把工具面收敛省下的上下文又填了回去。
2. **2026-07 主流客户端源码核实证明 `structuredContent` 支持分裂**：

| 客户端 | 是否消费 `structuredContent` | 2026-07 源码核实依据 |
| --- | --- | --- |
| **Claude Code / OpenAI Codex** | ✅ 支持 | 原生读取 `CallToolResult.structuredContent` |
| **Chatbox** | ❌ 不支持（仅读 `content`） | 经 `@ai-sdk/mcp@1.0.18` 接入，其 `toModelOutput` 忽略 `structuredContent`，仅将 `result.content` 转交模型 |
| **RikkaHub** | ❌ 不支持（仅读 `content`） | `McpManager.kt` 在 `client.callTool()` 后仅映射 `result.content`（`TextContent`/`ImageContent`） |

这证明 Markdown `content` 是所有客户端唯一通用的兼容地基，结构化载荷只能通过 MCP 原生的正交字段 `structuredContent` 按需挂载。

### 3.2 控制面三方案对比：为什么选“连接/环境变量级 `output_channel`”？

| 候选控制面 | 优点 | 核心缺陷与裁决 |
| --- | --- | --- |
| **1. Per-call 工具参数** | 表面上最灵活 | ❌ **否决**：客户端是否支持 `structuredContent` 是宿主程序的静态属性，MCP 握手并不向模型暴露该信息；让 LLM 逐次调用去猜一个它无从得知的参数，不仅永远只会用默认值，还会白白膨胀 23 个工具的输入 Schema。 |
| **2. 仅进程级环境变量** | 实现最简单，适合单用户 `stdio` | ⚠️ **仅对 `stdio` 足够，对 HTTP 不足**：一个常驻 Streamable HTTP 服务端可能同时被 Chatbox（不支持 `structuredContent`）和 Claude Code（支持）并发连接，进程全局开关无法同时满足两类客户端。 |
| **3. `stdio` 环境变量 + HTTP 连接/请求级覆盖（最终选定）** | 零工具 Schema 膨胀，且支持多客户端按连接定制 | ✅ **选定**：`stdio` 读取环境变量 `PRTS_OUTPUT_CHANNEL`（注：在 P1 后续审查中专门从最初无前缀的 `OUTPUT_CHANNEL` 改为带前缀的 `PRTS_OUTPUT_CHANNEL`，防止在 Docker/CI 共享环境中撞名）；HTTP 在会话 `initialize` 创建 `McpServer` 时按 `query ?output_channel= > header x-prts-output-channel > env PRTS_OUTPUT_CHANNEL > "content"` 优先级解析并由工具闭包捕获。 |

### 3.3 FastMCP 自动包装陷阱与 P1 Spike 技术实证

在实现双通道时，团队首先在 Python 侧通过 `list_stages` 开展了 P1 可行性预研（Spike），揭开了 Python FastMCP 与 TypeScript MCP SDK 在底层结果构造上的关键差异：

- **Python FastMCP 的隐式自动包装问题**：
  - 当工具函数返回类型注解为 `-> str` 时，FastMCP 会自动在工具清单中生成 `outputSchema={"result": "string"}`，并在每次返回时把同一份 Markdown 文本再包装一份 `structuredContent={"result": markdown}`，导致支持 `structuredContent` 的客户端收到双倍冗余文本；
  - 当工具函数直接返回 `dict` 时，FastMCP 虽然会填充 `structuredContent`，但同时会自动往 `content` 里硬塞一个序列化后的 JSON 文本块，覆盖掉人类可读的 Markdown。
- **Spike 破局方案（`-> object` + 显式 `CallToolResult`）**：
  - 源码核查证实，FastMCP 底层 Server 对 `isinstance(results, CallToolResult)` 分支会**原样透传 `CallToolResult`，既不追加额外 JSON 文本块，也跳过自动 `outputSchema` 校验与声明**。
  - 因此，Python 侧将所有工具的返回类型注解统一改为 `-> object`：17 个结构类工具拆分为 `build_<x>(args) -> dict | None`（唯一事实源）与 `render_<x>(dict) -> str`（纯渲染），经 `render_result(data, markdown, channel)` 显式返回 `CallToolResult`；6 个纯叙事类工具（`get_operator_archives`、`get_operator_voicelines`、`read_story`、`read_activity`、`get_story_summary`、`prts_page`）也在 P2a 阶段统一经 `text_result(markdown)` 改为返回 `CallToolResult(content=[markdown], structuredContent=None)`，从而一举消除了 `tools/list` 中的冗余 `outputSchema` 与双发文本（并专门编写了通过 `await mcp.call_tool(...)` 与 `await mcp.list_tools()` 校验透传行为与 `outputSchema is None` 的集成测试护栏）。
  - 同时，团队决定**不主动声明结构类工具的 `outputSchema`**：因为完整的返回结构 JSON Schema 同样会进入 `tools/list` 消耗大量上下文预算，省略 `outputSchema` 可最大化兑现 128K 上下文减负收益。
- **TypeScript SDK 的对称移植与 Golden Parity 夹具**：
  - TypeScript 侧使用的 `@modelcontextprotocol/sdk`（`server.tool`）本就是显式返回 `{ content: [...] }`，不存在 FastMCP 的字符串自动双发问题，因此 6 个叙事工具无需改动；
  - 为确保双实现的 `structuredContent` 逐字段完全同构，团队建立了跨语言共享的 Golden JSON 夹具目录 [`tests/parity-fixtures/`](../../tests/parity-fixtures/)，强制 TypeScript 的 `buildX()` 输出使用与 Python 完全一致的 `snake_case` 键名并通过深度相等断言；任何入参越界、无效正则或数据缺失错误均保持 `isError=false` 的纯文本 `textResult` 返回，确保 1.x 客户端升级后零破坏。
- **“兼容”口径的精确边界与合法空结果语义**：
  - 2.0 承诺的默认兼容特指 **content 文本兼容**——默认通道的 Markdown 文本保持 1.x 原貌，而非 manifest/wire 形状逐字节不变；已迁移工具的 wire 形状恰恰被有意改变，以移除 FastMCP 自动生成的 `outputSchema={"result": "string"}` 声明与重复的 `structuredContent={"result": markdown}` 包装；
  - 结构类工具的**合法空结果**经结构化通道返回空列表载荷：筛选无匹配时返回 `{total: 0}`（或 `{total: 0, entries: []}`）；分页 `offset` 超出末尾时列表字段为空数组、`total` 保留筛选全集计数并附 `empty_reason: "offset_out_of_range"`（如冻结夹具 `list_enemies_offset_empty.json` 所示）。content 通道仍原样输出原有的人类可读提示，使结构化消费方可以统一依赖“空 ⇒ 列表字段为空数组”；而无效参数、数据缺失等真实错误仍只经 content 文本返回，不塞入 `structuredContent`。
