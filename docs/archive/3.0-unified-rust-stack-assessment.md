# 3.0 统一技术栈选型评估：从双实现到原生 Rust

> **工程档案（2026-10 · v3.0.0 战略决策记录）**：本文整理自 2026-10-11 的《3.x 统一技术栈内部评估》、2026-10-11 技术栈评估证据快照与 2026-10-13 的《3.x Rust 迁移计划》，记录 PRTS-MCP 为什么决定结束 Python 与 TypeScript 双实现并行历史、当时选型时的真实输入条件与统计局限，以及最终收敛为原生 Rust 的边界约束。

---

## 1. 双实现的历史渊源与维护困局

在 0.x 初创期，Python 与 TypeScript 两套实现各有明确的生态位分工：Python 负责本地 `stdio` 子进程接入，TypeScript（2026-04 引入，由早期 SSE 快速演进为 Streamable HTTP）负责远程 HTTP 服务。
随着 `2.0.0`（2026-07-03）统一了 23 个工具契约与输出通道、**`2.3.0` 正式补齐了双端跨传输支持**（Python 支持 Streamable HTTP、TypeScript 支持 `stdio`），两套实现在功能面上已经 **100% 重叠**——用户只是按部署习惯选择运行时，而非按功能选择实现。

截至 2026-10-11（`v2.8.1` 发布时），工作树中两套实现的物理代码规模（含注释与空行）如下：

| 维度 | Python 实现（`python/`） | TypeScript 实现（`ts/`） | 合计维护规模 |
| --- | ---: | ---: | ---: |
| **业务源文件数** | 57 个文件 | 59 个文件 | **116 个源文件** |
| **业务源码物理行数** | 11,810 行 | 12,650 行 | **24,460 行** |
| **测试文件与行数** | 42 个文件（11,375 行） | 42 个文件（10,578 行） | **84 个测试文件（21,953 行）** |

维持双实现的边际收益已趋近于零，而边际成本却在每次迭代中成倍放大：
1. **双倍开发与双倍审计成本**：每次 SDK 升级、畸形输入边界处理、缓存失效、同步状态机调整、错误文案与数值舍入对齐，都必须用两种语言各写一遍，并在 Code Review 中反复证明两端一致。
2. **双实现相互参照 ≠ 独立正确性证明**：在 `2.8.1` 发布前的静态审阅中，既出现了“Python 补充目录校验漏掉列表类型守卫而 TS 已有”的单侧遗漏，也出现了“目录缓存身份追踪问题同时存在于 Python 与 TS 两端”的共犯错误。这证明双实现的互校价值完全可以转化为**单一活跃实现 + 跨版本冻结契约夹具（Golden & Parity Fixtures）**，无需长期维持两份业务代码。

### 2.2 必须保留的统计偏差与自动化噪声说明

原始评估报告专门警示了三项不可忽视的统计偏差，防止由下载量推导出失真结论：
1. **特定旧版本的集中拉取**：在 npm 最近一周（2026-10-03 至 2026-10-09，共 `1,982` 次下载）中，旧版 `2.7.2` 单版本占了 **`1,806` 次（91.12%）**，而最新稳定版 `2.7.4` 为 `111` 次。这种高度集中可能源于下游固定版本号的自动化集成或 CI 重复拉取。
2. **客户端环境标识缺失与 CI 流量**：同一 30 天 PyPI 的 `630` 次下载中，操作系统与 Python 次版本标识为 `null` 的高达 **`560` 次**（其余 70 次为 Linux `41`、Windows `15`、Darwin `14`）；GitHub 近 14 天 traffic 快照（`106` 次访问 / `33` 独立访客、`737` 次 clone / `170` 独立克隆来源）的高峰也明显与发版 CI 活动重合。
3. **结论边界**：上述数据证明 TypeScript 渠道近期的包分发活跃度显著高于 Python，但 Python 与 GHCR 镜像的历史存量绝非为零——因此**收敛单一实现的理由建立在“消除双倍工程维护成本 + 通过 LTS 分支履约保护存量用户”之上，而非建立在“假设 Python 用户为零”之上**。

## 4. 选型权衡：保留 TypeScript vs. 迁移原生 Rust

### 4.1 2026-10-11 选型评估时的真实输入条件（无后见之明）

需要明确历史时序：**在 2026-10-11 撰写《3.x 统一技术栈内部评估》第 4 节时，团队尚未编写任何 Rust 业务代码，也没有 Rust 版本的性能或内存实测数据**（当时评估表的“资源控制”一栏明确记为“有优化空间；本轮没有 Rust 性能数据”）。当时的对比完全基于工程客观条件：

| 评估维度 | 方案 A：收敛并仅保留 TypeScript | 方案 B：迁移并统一为原生 Rust |
| --- | --- | --- |
| **近期迁移与验证成本** | **优势明显**：几乎零重写成本，直接保留现有生产实现与全部已验证的边缘语义。 | **成本高昂**：重写期投入大，必须逐一重新验证 24 个工具、同步状态机、双时代协议与异常语义，且须防止形成长期并存的“第三套实现”。 |
| **CLI 与配置** | **可以充分胜任**。 | **同样适合**，且可提供原生可执行文件。 |
| **分发与运行时矩阵** | `npm` / `npx` 链路已完全成熟；但宿主机仍须安装 Node.js 或 Bun，Windows/macOS 桌面客户端常受运行时环境与 `.cmd` 包装困扰。 | 可消除终端用户的 JS 运行时依赖、提供单文件级原生可执行文件；但**新增了 5 平台（OS × 架构 × C 链接方式）的交叉编译与二进制发布矩阵成本**。 |
| **底层资源控制潜力** | 已有明确的 `Bun 1.3.14` 生产基线，但受制于 JS 引擎内存开销与流式/多线程限制。 | 具备消除运行时基底内存与精细控制同步/索引缓冲的潜力，但**必须靠后续纵向原型实测证明，不能仅凭语言特性空口承诺固定倍数的提升**。 |
| **MCP 生态成熟度** | 官方 Tier 1 SDK（`@modelcontextprotocol/sdk`）。 | 2026-10-11 核实官方 Rust SDK（`rmcp 3.5.1`，2026-10-05 发布）已同列官方 Tier 1，不再存在早期生态空白，但仍需实测其与现有 wire 契约的兼容性。 |
| **维护者长期意愿（非性能因素）** | 未被列为维护者长期偏好的演进方向。 | **维护者明确偏好 Rust**：作为长期个人/小团队维护的开源基础设施，维护者的长期投入意愿被诚实记录为合理的决策加分项（同时规定“偏好不能替代验证门禁”）。 |

### 4.2 从“阶段 B 纵向验证”到 2026-10-13 正式拍板的时间线

正是因为 2026-10-11 评估坚持“不凭语言光环直接公开承诺 3.0”，团队采取了**先在本地隔离完成 P0–P9 全量实现与同机基准验证、凭实证拍板后再进入 M0–M5 公开发布**的两步走决策链：
1. **2026-10-11（选型评估与风险立项）**：识别出 ECMAScript 正则兼容、数据同步与恢复、立绘增量链、工具输出精度、MCP 协议生命周期、多平台打包 **6 大重写高风险区**，批准在本地独立分支开展纵向攻关；
2. **2026-10-11 – 2026-10-13（P0–P9 本地完备验证）**：逐阶段完成 384 项离线 MCP 差分用例、QuickJS C 正则内核剥离与 P9 多核/单核同机性能实测（证实四核下冷索引提速 `2.72×`、热查询全面领先且常驻 RSS 从 `288–356 MiB` 压降至 `~123 MiB`，详见下一篇档案 [3.0 Rust 行为复刻、QuickJS C 正则剥离与原生性能报告](3.0-rust-parity-and-native-performance.md)）；
3. **2026-10-13（决策冻结与 M0 启动）**：在全部关键风险拿到实证闭环后，正式确立原生 Rust 为 3.x 唯一业务实现，并将管理 CLI、独立拆仓（`prts-mcp-python` 提案）及其他新产品特性明确排除在 3.0.0 首发范围之外。

## 5. 分发兼容与长期维护线（LTS）约束

在推进 M0–M5 切换时，评估确立了五项严格的外部兼容与维护线隔离准则：

1. **先建 `lts/2.8` 保护伞并继承 `#77` 渠道隔离**：
   - 早期讨论曾担心主线 workflow 会让 LTS 发布覆盖 `latest` 标签；核查 `origin/lts/1.7` 后确认，PR `#77` 早已为 1.7 LTS 建立了 `lts-1.7` npm dist-tag 并严禁 LTS 覆盖 GitHub `Latest` 与 Docker `:latest`。
   - 因此 `lts/2.8` 在切出时直接继承该隔离机制（使用 `lts-2.8` 与 Docker `:2` 标签），保留 Python 与 TypeScript 双实现，与 `lts/1.7` 一同维护至 **`2027-07-02` EOL**。
2. **npm 双入口与薄 Node 启动桥**：
   - 新增 `prts-mcp` 主包，同时保留原 `prts-mcp-ts` 包名与 `prts-mcp-ts`、`prts-mcp-ts-bun`、`prts-mcp-ts-stdio` 命令入口；底层统一通过 `@3akhp/prts-mcp-runtime` 轻量 Node 启动桥拉起对应平台的预编译 Rust 二进制。
3. **GHCR 公开镜像默认 `stdio` 兼容**：
   - 由于 2.x 时期公开的 `ghcr.io/3akhp/prts-mcp` 镜像是默认 `stdio` 模式的 Python 镜像，3.0 的原生 Rust Docker 镜像（`prts-mcp-ghcr` 入口）必须**继续保持默认 `stdio` 模式**（通过 `PRTS_TRANSPORT=http` 切换为 HTTP），绝不能草率套用旧 TS Dockerfile 的默认 HTTP 行为而破坏存量容器用户的配置。
4. **数据卷双向可回读**：
   - 原生 Rust 实现完全兼容 2.x 的 `/data/gamedata`、`/data/gamedata-levels`、`/data/storyjson`、`/data/images` 目录布局、`.gamedata_pair.json` 配对指针与共享卷目录锁，支持挂载旧卷无缝升级或回退至 `2.8.1` 镜像。
5. **所有公开渠道内置已激活备用数据**：
   - 五平台原生归档、npm 数据包（`@3akhp/prts-mcp-data`）与双架构 Docker 镜像统一内置经过校验的只读备用游戏数据，确保断网或首启期间立即可用。
